## 卡点 1｜看画面：`--headless` 和 `-s` 的作用

想直观理解失败长什么样，去掉 `--headless` 开窗口。两个坑：

**坑 A：`MUJOCO_GL` 被 env.sh 写死成 osmesa**

```bash
export MUJOCO_GL=glfw    # 从离屏渲染切到开窗口
```

| 值 | 用途 |
|---|---|
| `osmesa` | 软件离屏，**无显示器**（CI、Docker） |
| `glfw` | **开窗口**，有显示器时用 |
| `egl` | GPU 加速离屏 |

**坑 B：不加 `-s` 的话窗口一闪而过**

```
总时间: 0.22s      ← 真实时间
仿真时间: 3.45s    ← 虚拟时间
```

**快放 15 倍。** 加 `-s`（`--sync`）后两者都是 3.17s，时间比例 1.00。

**副产品**：退出时 `Segmentation fault (core dumped)`，发生在 `🎬 查看器已关闭` 之后，**不影响结果**。是 viewer 与 GL 上下文的清理顺序冲突。低优先级缺陷。

## 卡点 4｜追 BUCKET2 根因的四步

### 第一步：失败距离等于什么

`seed=13` 失败时 `dist=0.2378`，而两物体**初始间距也是 0.2378** → 方块根本没被搬动。

### 第二步：给状态机装探针

monkeypatch `set_target_from_primitive`，打印每步的方块高度：

```
seed=13:  #1 blk_z=0.7458 ... #10 blk_z=0.7458   ← 全程一微米没变
seed=2:   #5 blk_z=0.6861 → #8 blk_z=0.7772      ← 被抬起搬运
```

**同时排除 IK**：失败的 run 里「状态 N 设置失败」出现 **0 次**。

### 第三步：几何规律

转到 armbase 局部坐标：

| block 离基座 | 样本 | BUCKET2 失败 |
|---|---|---|
| < 0.315 m | 11 | **0** |
| ≥ 0.315 m | 19 | 10（53%） |

### 第四步：读接触数据 —— 唯一确凿的证据

```python
for i in range(d.ncon):
    c = d.contact[i]
    b1, b2 = m.geom_bodyid[c.geom1], m.geom_bodyid[c.geom2]
```

```
seed=13 全程:  方块接触 = ['table']              ← 夹爪从未碰到
seed=2  抓取时: 方块接触 = ['left','right','table']
```

`grip_ctrl` 从 0.04 → 0.0000，**夹爪确实合上了，但合在空气里**。

> 📌 **前三步大量推理，第四步一条数据定案。**
> **能读事实的时候，不要用数字去推。** 排查前先问：这个系统有没有直接暴露我要的事实？

## 卡点 5｜⚠️⚠️ 本日最重要：我下了一个错误结论

### 我当时的推理

测了闭合瞬间方块在末端坐标系中的位置：

| | seed=2（成功） | seed=13（失败） |
|---|---|---|
| 横向 | 7.9mm | 1.5mm |
| **轴向** | 4.1mm | **8.1mm** |

**结论**：「方块在夹爪够不到的深度上，根因彻底查清了。」

**这个解释看起来完美** —— 同时解释了「总距离相近却结果相反」和「接触列表里从未出现手指」。

### 扩大样本后

跑 20 个 seed，轴向 >7mm 的有 5 个：

| seed | 轴向 | 结果 |
|---|---|---|
| 0 | 10.0mm | FAIL |
| **4** | **7.5mm** | **OK** |
| 13 | 8.1mm | FAIL |
| **14** | **8.1mm** | **OK** ← 与 13 数值完全相同 |
| 16 | 9.5mm | FAIL |

四个候选变量的组间差异全在噪声范围内：

| 变量 | OK 均值 | FAIL 均值 | 差 |
|---|---|---|---|
| 轴向 | 4.06mm | 5.53mm | +1.5 |
| 横向 | 4.95mm | 4.69mm | −0.3 |
| blk_z | 0.666 | 0.689 | +0.02 |
| reach | 0.324 | 0.355 | +0.03 |

**假设证伪。**

### 我为什么会犯这个错

**用两个样本的对比就下了结论。**

任何两次运行之间都有几十个数值不同，**总能挑出一个「看起来像原因」的** —— 而它必然能解释这两个样本，因为你就是从它们身上挑出来的。

**统计上这叫过拟合到样本：解释力 100%，泛化能力 0。**

### 最讽刺的部分

我在 Day 5 tutorial 的 §2.4 亲手写下过：

> 「两个样本的某个数值不同」不等于「那就是原因」—— 必须看整体分布。

**然后在下一轮里违反了它。**

> 📌 **知道一条原则，和在压力下遵守它，是两件事。**
> 找到「完美解释」的瞬间最危险 —— 那种「终于搞定了」的感觉会让你停止验证。

### 修正后的结论

不写「根因是 X」，改写分层结论：

```
已排除：IK（0.5mm，优于成功组）、手臂到位（8.3mm，优于成功组）
已确认：夹爪闭合时与方块零接触
已证伪：轴向深度假设、桌面高度假设
弱相关：离基座 >0.315m（必要不充分）
未确定：根因
```

## 卡点 6｜写 `test_task_matrix.py` 的三个设计决策

### 决策 1：用 subprocess 而非进程内调用

`universal_task_runtime.main()` 会加载 MuJoCo、创建编码器、写文件。进程内重复调用会累积全局状态（Day 2-4 反复遇到的主题）。

**代价 ~0.3s 启动开销，换完全隔离。值得。**

### 决策 2：采样器不做成功断言

45 个组合一大半会永远红。**唯一的断言是「不能是 BUCKET4」** —— 那是确定性缺陷，应该被修，不该被当成 flake 容忍。

### 决策 3：marker + 默认排除

```toml
addopts = "... -m 'not flake'"
```

**不这么做的话，`pytest tests/` 从 3 秒变 81 分钟，没人会再跑测试。**

验证生效：`113 passed, 45 deselected in 3.04s`。

## 卡点 7｜验证分桶：绿灯毫无信息量

小规模验证 `5 passed`，但**这不能说明分桶对了** —— 测试只在 BUCKET4 时 fail，其他一律 PASS。

**必须去看 `record_property` 记了什么。**

### 解析代码写错了

```python
dict(t.get("user_properties", []))
# ValueError: dictionary update sequence element #0 has length 1; 2 is required
```

**真实结构**：

```python
[{'robot': 'airbot_play'}, {'bucket': 'SUCCESS'}, {'dist': 0.0032}]
```

是**一串单键字典**，不是 `(k, v)` 元组列表。

> 📌 `record_property("robot", "x")` 在内存里是元组，但导出 JSON 时被转成了 `{"robot": "x"}` —— **JSON 没有元组类型**。
> **不要假设导出格式和内存格式一致。** 第一次接触任何序列化产物，先 `print(repr(...))`。

### 用确定性定向验证 BUCKET2 分支

10 次采样撞到了 SUCCESS 和 BUCKET1，但 **BUCKET2 一次没出现** —— 那条分支从未被执行过。

**用 `seed=13` 定向制造**：

```
BUCKET2_判据失败  state=10/10 dist=0.2378
BUCKET2_判据失败  state=10/10 dist=0.2378
BUCKET2_判据失败  state=10/10 dist=0.2378
```

**三条分毫不差。** 同时第三次确认了端到端确定性 —— 这次是通过完整的 pytest + subprocess 管道。

**5 条分桶分支验证了 4 条**（BUCKET3 缺，没有真会卡住的组合）。

## 卡点 9｜热力图的 NaN 白格 bug

`cover_cup` 那行有 4 格是 **100% 配置崩溃** → `rate` 为 NaN → `imshow` 画成**白色**。

**白色会被误读为「没测试」，而实际是「测了，每次都崩」。**

修复：

```python
cmap = plt.get_cmap("RdYlGn").copy()
cmap.set_bad("#9e9e9e")                       # NaN 染灰
im = ax.imshow(np.ma.masked_invalid(rate), cmap=cmap, ...)
```

> 📌 **可视化里「缺失」和「零」必须能被区分。**
> 这个 bug 不改，读者会以为那几格没数据 —— 而它们恰恰是最需要被看见的。

## 卡点 10｜保存数据时 `.gitignore` 踩了两次

2.3MB 的 JSON 里 93% 是 pytest 元数据，先瘦身成 155KB 的 CSV。然后：

| 尝试路径 | 被谁挡 | 原因 |
|---|---|---|
| `data/experiments/` | `.gitignore:7` `data` | **无斜杠模式匹配任意层级** |
| `docs/data/` | 同上 | 同样被匹配到 |
| `docs/experiments/*.json` | `.gitignore:14` `*.json` | 全局忽略 JSON |
| **`docs/experiments/*.csv` + `*.yaml`** | — | ✅ |

> 📌 **`.gitignore` 模式匹配**
>
> | 写法 | 范围 |
> |---|---|
> | `data` | **任意层级**的 data |
> | `/data` | **仅根目录** |
> | `data/` | 任意层级的 data **目录** |
>
> **`git check-ignore -v <文件>` 直接告诉你是哪一行挡的** —— 比猜快得多。

### 关于「要不要存进 git」的讨论

这不是显然正确的决定。反对理由都成立：git 不适合存数据、代码仓库应该只放代码、数据会过期。

**最终决定：暂存，但写下退出条件。**

```yaml
retention:
  rationale: 155KB 换「结论可复算」。数据含随机性，重跑得不到同一份。
  exit_condition: 累积约 10 份实验（~1.5MB）时迁 Git LFS 或 CI artifact。
```

> 📌 **「暂存」和「随便存」的区别是：你知道退出条件。**
> 没有退出条件的临时方案，三年后还在，而且没人敢动。
