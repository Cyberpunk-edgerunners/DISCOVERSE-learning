## 一、「配置无效」和「配置无效且有害」是两回事

Day 3 建立了「未消费的配置」这个缺陷模式。Day 4 发现**同一模式下严重度可以差一个数量级**。

判据只有一条：**如果它生效了，行为会变吗？**

| 缺陷 | 配置声明 | 实际生效 | 生效后 | 严重度 |
|---|---|---|---|---|
| **J** | `collision_radius: 0.12` | 0.05 | **行为大变**（避让距离 2.4×） | 高 |
| **O** | `dt: 0.002` | 0.001 | **解逐位相同** | 低 |

两者都是「代码没读配置」，危害天差地别。

**不要因为缺陷模式相同就假设严重度相同。** 模式识别帮你**发现**缺陷，但**定性**必须靠实测。

### 为什么 dt 会约掉

```python
velocity = mink.solve_ik(configuration, tasks, dt, ...)   # 内部：误差 ÷ dt = 期望速度
configuration.integrate_inplace(velocity, dt)             # 速度 × dt = 位移
```

一除一乘。dt 唯一的作用是给速度限制提供量纲 —— 而当前配置没有 `VelocityLimit`。

## 二、休眠缺陷（latent defect）

「当前不可达」有两种，处置完全不同：

| 类型 | 例子 | 处置 |
|---|---|---|
| **结构性不可达** | 被 `if False` 挡死、函数无人调用、死代码 | 可删可忽略 |
| **条件性不可达** | 需某配置/功能开启才显现 | **记录，因为条件会变** |

`dt` 是第二种 —— 不是「不会发生」，是「**还没发生**」。

一旦有人加 `mink.VelocityLimit`（真机限幅是很自然的需求），配置写 0.002 实际按 0.001 算，**限幅严一倍**，IK 变慢或不收敛，而配置文件看起来完全正确。

**这就是缺陷 J 的剧本重演** —— 配置写着一个值，代码用着另一个，没人能从配置文件看出问题。

Day 3 的缺陷 S（贴图随机源）同类：if 分支现在走不到，`TEXTURE_1K_PATH` 一配好就活了。

## 三、修 or 不修：判断公式

**比的是「修的成本 + 风险」和「不修的期望损失」，不是「现在有没有影响」。**

| 缺陷 | 修的成本 | 不修的期望损失 | 结论 |
|---|---|---|---|
| O（dt） | **一行，实测零风险** | 将来限幅严一倍且难排查 | ✅ 修 |
| S（贴图） | 改公共函数签名 + 4 个调用方 | 贴图不可复现（不影响位姿） | ⏸ 记录，不修 |
| H（qpos_dim） | 改数字很容易，但**语义未定义** | 静默丢关节 | 🔍 先定义，再改 |

**如果 dt 的修复要改 20 行且有回归风险，正确答案就变成「记录，不修」。**

## 四、测试没有可观测差异就不要写

Step 5 原计划走完整 TDD（红 → 修 → 绿）。实测发现修复前后逐位相同 —— **写不出会红的测试**。

强行写一条会得到什么？

```python
def test_dt_comes_from_config():
    assert solver.dt == 0.002      # ← 这条【本来就绿】，self.dt 一直被正确赋值
```

**这是永远为真的断言**，Day 2 方法论第 1 条早就否定过它。

> 📌 **重要区分：`self.dt` 被正确赋值 ≠ `self.dt` 被使用。**
>
> 属性存在且值正确，任何检查 `solver.dt` 的测试都会通过。这解释了为什么 linter 抓不到 —— `self.dt` 有写无读，但类属性的「无人读取」几乎无法静态判定（可能被子类或外部读）。
>
> **要断言「配置改变导致行为改变」，而不是「配置被正确加载」。前者测契约，后者只测 getter。**
>
> 而当行为根本不会改变时（本例），**正确答案是不写**。

**永远为真的断言是负债不是资产**：它占维护成本、给人虚假安全感、重构时还得跟着改。

## 五、状态泄漏的判定标准

判据不是「对象有可变字段」，而是：

> **「调用 N 次后的输出，是否只由第 N 次的输入决定？」**

用这条重新审视 `MinkIKSolver`：

| 字段 | 每次入口重置 | 泄漏 |
|---|---|---|
| `self.configuration` | ✅ [solve_ik:99](../../discoverse/universal_manipulation/mink_solver.py#L99) 被 `current_qpos` 覆盖 | ❌ **不泄漏** |
| `posture_task` target | ❌ 只在给 reference 时更新 | ✅ **泄漏** |

**这是纯函数（pure function）思想的实用版本**：相同输入必得相同输出。

测试开发对纯函数最友好，对有隐藏状态的对象最头疼 —— 因为你必须**枚举可能的历史**才能覆盖行为。

### 与 Day 3 seed 缺陷的同构性

| | seed 缺陷 | posture_task 泄漏 |
|---|---|---|
| 表现 | 相同配置 → 不同场景 | 相同输入 → 不同解 |
| 根因 | 全局随机流是隐藏状态 | 对象字段是隐藏状态 |
| 后果 | 不可复现 | 不可复现 |

**都是「隐藏状态让相同输入得到不同输出」。** 这是可复现性问题的通用形态。

## 六、三次调用的对照实验设计

要证明「泄漏」，两次调用不够：

```python
x = solve_ik(tgt, mat, q)                       # 第1次：不传 reference
y = solve_ik(tgt, mat, q, reference_qpos=ref)   # 第2次：传   ← 污染源
z = solve_ik(tgt, mat, q)                       # 第3次：不传
```

**只跑前两次**会看到结果不同 —— 但那是应该的，输入本来就不同（一个传 reference 一个不传）。

**必须有第 3 次**，才能构造出「输入与第 1 次完全相同，唯一差别是中间发生过事」的对照。

> 📌 **对照实验的核心是「只变一个量」。**
> 第 1 次 vs 第 3 次：输入相同，差别只在「中间发生过什么」。
> 无状态对象里这个差别不该影响结果。它影响了 → 有泄漏。

### 附带的坑：让被测系统处在正常工作状态

第一次实验我随手编了目标坐标 `[0.35, -0.1, 0.9]`，结果 `converged=False` 跑满 50 次迭代。

那时测试「红」了，但红的原因是**目标不可达**，和状态泄漏毫无关系。

**从当前末端位姿偏移一小段**，保证目标一定可达 → IK 一定收敛 → 剩下的差异才能归因到你要测的东西。

**这和 Day 3 的「一个测试只能有一个失败原因」是同一条。**

## 七、⭐ 一个缺陷的修复里可能藏着两个独立契约

**本课最有价值的发现，来自一次「失败」的变异验证。**

`posture_task` 的修复实际做了两件事：

| 改动 | 作用 |
|---|---|
| 把 `set_target_from_configuration` **挪出 if 块** | **消除泄漏** |
| 补 else 分支恢复 `_default_posture_qpos` | **保持默认姿态是 home** |

**这两件事碰巧由同一段代码实现，但可以被独立破坏。**

实测三种写法：

| 写法 | 不传 reference 时的 posture 目标 | 泄漏 |
|---|---|---|
| 原代码 | 完全不设 → 沿用上次 | ✅ |
| 挪出 `set_target`，**无** else | `mink.Configuration` 默认值 = **qpos0** | ❌ |
| 挪出 `set_target`，**有** else | `key(0).qpos` = **home** | ❌ |

实测（airbot_play）：

```
mink.Configuration(model) 新建 -> [0, 0, 0, 0, 0, 0, ...]                    = qpos0
model.key(0).qpos（home）      -> [0, -1, 1.2, 1.5708, -1.2, -1.5708, ...]
```

**差得很远**，会影响冗余自由度下选哪个解。

**所以 else 分支的作用不是修泄漏，是「保持原有默认行为」。**

> 📌 **只写一条测试守住其中一个契约，另一个就在裸奔。**
>
> 这在实践中极其常见：一次修复顺手改了好几件事，测试只覆盖了最显眼的那件。

## 八、变异验证「没红」时的三种可能

Day 3 学的是「注入 bug，测试必须红」。Day 4 遇到了它**没红**的情况。

第一反应容易是「测试写错了」。**实际有三种可能：**

| 可能 | 如何区分 |
|---|---|
| A. 测试写错了 | 检查测试逻辑；注入一个**必然**破坏契约的变异看它红不红 |
| B. 修复不是你以为的那样 | **看 `git diff`** —— 你可能改了两处，真正生效的是另一处 |
| C. **契约不完整** | 测试守的那条契约确实没被破坏，但还有别的契约没人守 |

**本课是 C。** 泄漏测试守的「不泄漏」契约确实完好（因为泄漏被另一处改动修着），缺的是「默认姿态是 home」这条。

### 排查手段：先看 diff，别先猜

```bash
git diff <文件>
```

看清「我到底改了几件事」，比任何推测都快。

### 补测后的验证

再次注释 else：

```
FAILED test_default_posture_target_is_home_not_qpos0
1 failed, 2 passed          ← 只有新测试红，另两条仍绿
```

**这个「只红一条」的分布本身是证据**：说明两个契约被精确区分开了，而不是一个测试同时守两件事（那样红了又分不清）。

## 九、变异验证的第二重价值：暴露你对修复的误解

教程 §6.6 初稿把 else 分支写成「修复的关键」。**那句话是错的。**

跳过变异验证的话，会带着这个错误认知继续 —— 直到某天有人删掉 else，**泄漏没回来但默认姿态悄悄从 home 变成 qpos0**，而完全想不通哪里出了问题。

> **绿灯从来不是证据。能对已知的破坏做出反应，才是证据。**

变异验证不只验证「测试有效」，它同时验证「**你对因果关系的理解是否正确**」。

## 十、`XPASS(strict)` 的完整语义

Day 3 学了 `xfail`。Day 4 第一次**亲眼见到** `strict=True` 起作用。

| 状态 | 全称 | 含义 |
|---|---|---|
| XFAIL | e**X**pected **FAIL** | 预期会失败，**确实失败了** ✅ |
| **XPASS** | e**X**pected fail, but **PASS**ed | 预期会失败，**却通过了** ⚠️ |

修完代码后：

```
[XPASS(strict)] 缺陷 U：mink_solver.py:120 的 posture_task target...
FAILED tests/unit/test_mink_solver.py::test_posture_target_does_not_leak_across_calls
```

**红灯是「你修好了但忘了撤标记」的提醒，不是失败。**

注意 pytest 把 `reason=` 的文字**原样打印**了 —— **`reason` 不是注释，是会被展示的运行时信息**。写得越具体，看到这行的人越省事。

### 撤标记后测试不删

它从「缺陷证明」变成「**回归测试**」—— 守着这个 bug 不再回来。将来有人重构 `solve_ik` 弄丢了 else，测试会立刻红。

## 十一、「哪里没有反馈，哪里就有缺陷」

Day 2 记下的观察，Day 4 有了完整数据支撑：

| 字段 | 写错的后果 | 9 个机器人的正确率 |
|---|---|---|
| `ctrl_dim` | `data.ctrl[:] = 长度不符数组` → **立刻 ValueError** | **9/9 全对** |
| `qpos_dim` | `qpos[:9]` 在 `nq=15` 上**完全合法** → 静默丢后 6 个 | **4/9 出错** |

**会炸的字段维护得好，不会炸的字段积累错误。**

> **测试的本质工作，就是给那些原本不会炸的地方装上会炸的机制。**

这句话可以直接用在面试回答里 —— 它把「为什么要写测试」从「保证质量」这种空话，变成了一个**有数据支撑的机制描述**。

## 十二、调查的产出可以是「定义问题」而不是「修复问题」

缺陷 H 的根因查清了（夹爪 8 连杆），但**没有改数字**。

因为 `qpos_dim` 的语义**本身没有定义**：

- 指模型的 `nq`（15）？
- 还是「可控自由度」（7 臂 + 1 夹爪 = 8）？

iiwa14 那 8 根连杆是**被约束绑定的从动关节**，算 1 个还是 8 个取决于你问谁。

**在语义有共识之前，改数字只是把一个错误换成另一个错误。**

### 产出的形式：升级 xfail 的 reason

| | 交接内容 |
|---|---|
| 改之前 | 「iiwa14 的 qpos_dim 不对，差 6，原因不明」 |
| 改之后 | 「差 6 = 夹爪 8 连杆按 2 手指算；**待决策：qpos_dim 语义未定义**」 |

第二种，下一个人可以**直接开始决策**；第一种，他要重新调查一遍。

> **把「原因不明」升级为「根因已知 + 待决策点明确」，本身就是产出。**

## 十三、修复应恢复「本来该有的行为」

Day 3 学过（新增可选参数的默认值必须等价于旧行为），Day 4 第三次现身。

`posture_task` 不传 reference 时该恢复到什么？

| 候选 | 语义 | 评价 |
|---|---|---|
| **`key(0).qpos`（home）** ✅ | 和构造时 `_setup_ik_tasks` 一致 | **保持原有默认** |
| `current_qpos` | 「保持当前姿态」 | 说得通，但是**行为变更** |
| `qpos0`（不加 else 的结果） | 模型默认位形 | 与原设计不符 |

**修复不是重新设计的机会。** 顺手改成「我觉得更好的行为」，会让 bugfix 变成 breaking change —— 而使用者只看到版本号里的补丁位变了。

## 十四、Day 4 方法论清单

1. **「配置无效」和「配置无效且有害」是两回事。** 判据：如果它生效了，行为会变吗？
2. **模式识别帮你发现缺陷，定性必须靠实测。**
3. **休眠缺陷值得记录。** 「条件性不可达」的条件会变；「结构性不可达」才可忽略。
4. **修 or 不修，比的是「修的成本 + 风险」和「不修的期望损失」**，不是「现在有没有影响」。
5. **测试没有可观测差异就不要写。** 永远为真的断言是负债。
6. **属性被正确赋值 ≠ 属性被使用。** 要断言「配置改变导致行为改变」。
7. **状态泄漏的判据**：调用 N 次后的输出，是否只由第 N 次的输入决定？
8. **对照实验的核心是只变一个量** —— 证明泄漏需要三次调用，不是两次。
9. **让被测系统处在正常工作状态**，否则观察到的失败与你要测的无关。
10. **一个缺陷的修复里可能藏着两个独立契约。**
11. **变异验证「没红」有三种可能**：测试错、修复不是你以为的那样、**契约不完整**。先看 `git diff`。
12. **变异验证还能暴露你对因果关系的理解是错的。**
13. **绿灯从来不是证据；能对已知的破坏做出反应，才是证据。**
14. **`reason` 不是注释，是会被展示的运行时信息。**
15. **「哪里没有反馈，哪里就有缺陷。」**
16. **调查的产出可以是「定义问题」而不是「修复问题」。**
17. **修复应恢复「本来该有的行为」**，不要顺手改成别的。
18. **先证明，再动手** —— Day 4 开工前四项调查，计划文档三条推断错了两条。

### 附：新增的第四条最值得记

前三条是「别人写的文档错了」，第四条是「**我自己刚写的解释错了**」。

而且它不是靠读代码发现的 —— **是变异验证抓出来的**。这说明：

**对自己修复的理解，也需要一个外部检验机制。读一遍代码觉得「应该是这样」是不够的。**
