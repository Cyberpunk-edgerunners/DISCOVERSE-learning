## 一、测试设计：一个测试只能有一个失败原因

计划文档原话是断言「完整轨迹逐帧相同」。**实际选的是「随机化后的物体初始位置」。**

| 候选断言对象 | 问题 |
|---|---|
| 最终任务成功/失败 | 粒度太粗；成功率相同不代表轨迹相同；单次几十秒 |
| **每一帧 qpos** | 粒度对，但**引入了物理引擎的浮点不确定性**。红了分不清是 seed 问题还是 MuJoCo 问题 |
| **随机化后的初始位置** ✅ | 纯 PRNG 问题，不涉及物理步进，毫秒级，红了原因唯一 |

**职责混淆**：选轨迹会让测试同时承担「seed 是否生效」和「物理引擎是否确定」两个职责。一旦红了，要先花半小时判断是哪一个。

**回报是可测量的**：全套确定性测试 1.63s 跑完。跑完整任务的话是几十秒，且不可归因。

## 二、容差的判据是「理论上应该差多少」

计划文档写 `rtol=1e-5`，**实际用 `atol=0`（严格相等）**。

PRNG 是**确定性算法** —— 同 seed 同状态必然产出逐比特相同的 float64。这里没有浮点累积误差的余地。

| 场景 | 理论误差 | 该给的容差 |
|---|---|---|
| 纯 PRNG 复现 | 0 | `atol=0` |
| 浮点物理累积 1000 步 | 有 | `rtol=1e-9` 量级 |
| 神经网络跨 GPU | 更大 | `rtol=1e-3` |

**给宽容差是在掩盖你不理解误差来源。** 判据不是「差多少算能接受」，而是「理论上应该差多少」。

### 副产品：失败数字变得可解释

实测最大偏差 **0.336m**，而随机化范围是 `x_range: [0.2,0.4]` / `y_range: [-0.2,0.2]`。

**偏差和随机化范围同量级** → 说明是两次完全独立的抽样，不是「seed 生效了但有数值误差」。

若偏差是 1e-9 才是浮点问题。**好的失败信息不只是「友好」，它直接缩短根因定位时间。**

## 三、未消费的配置：一类独立的缺陷模式

实测断链：

```
配置层：  6 处声明 seed: null
              ↓
              ✂️  0 个 Python 读取者
              ↓
代码层：  randomization.py 25 处裸 np.random.*（numpy 全局流）
         utils/__init__.py:90 random.choice（stdlib，独立源）
         utils/__init__.py:97 np.random.randint（numpy 全局流）
```

### 为什么它比「配置写错」危险

| | 配置写错 | 配置没人读 |
|---|---|---|
| 表现 | 通常会炸或行为异常 | **改配置完全没反应** |
| 使用者反应 | 去查配置 | 「哦，大概仿真本身就有不确定性吧」 |

**缺陷成功伪装成了系统的固有属性。**

### 更糟的是注释在描述不存在的功能

```yaml
seed: null    # 随机种子（null表示使用系统时间）
```

这条注释（出现 2 处）**在描述一个从未实现的功能**。使用者读到它会合理地相信 seed 可用。

**同一模式的其他现身**：缺陷 J（`collision_radius` 键名不匹配）、缺陷 O（`dt` 被硬编码遮蔽）、Day 2 缺陷 B（`camera_configs` 返回空列表）。

defect-inventory 第七节把这个模式总结为「**静默的空集合与未消费的配置**」。

## 四、多随机源：seed 一个不等于 seed 全部

一个进程里可以有多个互不相干的随机源：

| 源 | 归谁管 | 怎么设种子 |
|---|---|---|
| `random.*` | Python 标准库 | `random.seed()` |
| `np.random.*` | numpy **全局单例** | `np.random.seed()` |
| `np.random.Generator` | numpy **实例** | `default_rng(seed)` |
| `torch` / CUDA cuDNN | PyTorch | `torch.manual_seed()` + 算子确定性开关 |

**打比方**：两根独立水管。关掉一个，另一个照样出水。

PyTorch 官方复现指南要求同时设 4 处 seed，即便如此仍不保证跨 GPU 一致。

### Day 3 的实际教训：随机性从 import 边界溜走

修复范围是 `randomization.py`，25 处全改成 `self.rng.*`。但：

```python
# randomization.py:553
random_texture_pil = get_random_texture()   # ← 调用另一个文件的函数
```

`utils.get_random_texture()` **完全不知道 rng 的存在**，两个分支各用一种未受管控的随机源。

> **确定性的边界不是「我改过的文件」，而是整条调用链。**
> 查随机源要跟着调用走，不能只 grep 单个文件。

## 五、全局可变状态是测试的头号敌人

为什么选 `np.random.Generator` 实例而非 `np.random.seed()` 全局种子：

### 理由 1｜全局状态是共享的，你控制不了谁在用

`np.random.seed()` 修改的是**进程级全局单例**。seed 完之后，任何第三方库（mujoco 工具、matplotlib、mink）调一次 `np.random.*` 都会推进这个状态。

### 理由 2｜并行测试会互相污染

已装 `pytest-xdist`。多 worker 同时动全局 seed → 「单跑绿、`-n 8` 跑红」。

**这和 Day 2 学的 fixture 作用域是同一条原则：可变的共享状态必须隔离。**

### 理由 3｜NumPy 官方已弃用其推荐地位

NEP 19 建议新代码用 `Generator`。`RandomState`（旧 API）保留只为向后兼容。

### 这条原则的反复现身

| 天 | 场合 |
|---|---|
| Day 2 | fixture 作用域（`MjData` 必须 function 级） |
| **Day 3** | **全局 PRNG** |
| Day 3 | 一个测试内部的两次「运行」也必须各自新建 `MjData`/`SceneRandomizer` |
| Day 10-11（预期） | CI 并行 job 共用临时目录 |

## 六、Generator 不是旧 API 的简单包装

25 处替换里，23 处是纯机械改名，**2 处需要动脑**：

| 旧 API | Generator | 为什么变了 |
|---|---|---|
| `random(3)` / `uniform` / `normal` | 同名 | 无问题，保留 |
| **`rand(2,3)`** | **`random((2,3))`** | 和 `random` **功能重复**，只是参数风格不同 → 删掉 |
| **`randint(n)`** | **`integers(n)`** | 名字没说清上界开闭 → 改名并加 `endpoint` 参数 |

**这不是「陷阱」，是 NumPy 故意的 API 清理。** 重新设计时顺手清理了历史包袱。

## 七、状态的「家」在哪一层：一个设计决策

seed 该在**构造时**传入，还是**每次调用**传入？

| 方案 | 语义 | 适用 |
|---|---|---|
| **构造时 seed** ✅ | 一个对象 = 一条随机流，多次调用继续往下吐 | 本项目 |
| 每次调用 seed | 每次调用都重置 | 「精确复现第 N 次调用」 |

**选构造时的理由**：随机数生成器**是有状态的**。它不是「给个 seed 算个数」，而是「从 seed 出发连续往下吐数」。这条流需要一个稳定的家。

如果 `exec_randomization` 每次重设 seed，**连续调用两次会得到完全相同的场景** —— 几乎肯定不是使用者想要的。

**两种都有正当用途，但不能混。** 混了会出现「我以为在往下吐，其实每次都重置」的诡异 bug。

## 八、新增可选参数的默认值必须等价于旧行为

```python
def __init__(self, mj_model, mj_data, seed: Optional[int] = None):
    self.rng = np.random.default_rng(seed)
```

**为什么默认 `None` 而不是 `0` 或 `42`**：

`default_rng(None)` 从操作系统熵源取种 —— 等价于原来「不指定就随机」。

给固定默认值会让**所有不传 seed 的调用方突然变成同一个固定序列**。原本每次场景都不同的人，升级后发现场景再也不变了 —— **行为破坏**，而使用者没改任何代码。

## 九、`.get(k, default)` 的陷阱，第二次现身

Day 2 缺陷 C 教过：**`.get()` 的 default 只在键不存在时生效。键存在但值为 `None` 时返回 `None`。**

而 YAML 里 `settings: null` 完全合法。所以：

```python
_rand_cfg.get('settings', {})       # settings: null 时返回 None → 下一步 .get() 炸
(_rand_cfg.get('settings') or {})   # ✅ or 把 falsy 值统一兜住
```

### 但这次的 `None` 恰好安全

`seed` 取到 `None` 是**我们想要的** —— `default_rng(None)` 接受它。

**关键**：要能说出「为什么不咬人」，而不是「碰巧没事」。

> **同样的取值模式，安全与否取决于下游怎么用。**
> 缺陷 C 里 `None.get()` 会炸，是因为下游把它当 dict；这里下游是 `default_rng()`，它接受 `None`。

## 十、为可测性重构，不是为测试牺牲设计

缺陷 J 的取半径逻辑埋在两层 `for` 循环里的局部变量：

```python
for attempt in range(max_attempts):
    for obj_config in objects_config:
        for obj_attempt in range(10):
            radius = obj_config.get('min_distance', 0.05)   # 测试拿不到
```

### 三个方案的对比

| 方案 | 做法 | 用「有人换成第三个键名 `radius`，谁会红」检验 |
|---|---|---|
| A | 断言「`min_distance` 键不该被读」 | ❌ 测的是**某个具体的错误名字**，不是行为 |
| B | monkeypatch `_check_collision_2d` 偷参数 | ✅ 会红，但要复刻被替换函数的行为、和签名焊死、戳私有方法 |
| **C** | **抽成 `_get_collision_radius()`** ✅ | ✅ 会红，且零 mock、零依赖、毫秒级 |

### mock 的代价

每用一次 monkeypatch，就在测试和**实现细节**之间新增一根绳子。改一行生产代码断十个测试，而那十个没有一个发现了真 bug —— **假警报是最消耗信任的失败**。

**判断标准**：你在替换**外部依赖**（网络、时钟、文件系统），还是**自己家的代码**？后者往往说明代码结构有问题。

### 关键认知

「这段逻辑没法测」通常是**设计信号**，不是测试的困难。

这次重构**没有为测试增加任何东西**（没加 `if testing:`、没把 private 变 public），只是把一段有独立业务含义的逻辑给了个名字。重构完代码**本身更清楚了** —— docstring 现在能解释「为什么兼容两个键名」，而原来那行代码没地方写这个。

> **TDD 最被低估的收益：它逼你把纠缠的逻辑拆开。**

## 十一、变异测试：验证「测试本身有效」

**核心逻辑：故意植入 bug，好的测试套件应该红。** 全绿说明测试是摆设。

### Day 3 的三次注入

| 注入的真实修复失误 | 谁抓到了 |
|---|---|
| `default_rng(seed)` → `default_rng(None)`（忘了用） | 2 条红 |
| task_base 不传 seed（**忘了接线**） | **只有接线测试红** |
| `default_rng(42)`（**seed 写死**） | **只有异 seed 测试红** |

**后两种各自只有一条测试能抓到** → 实测证明四条测试缺一不可。

### 手工版比工具版更聪明的地方

自动化工具（`mutmut`、`cosmic-ray`）随机改符号。手工注入的三个变异对应**三种真实的修复失误**，针对性更强。

### 入门版就是 Day 2 方法论第 1 条

「新写的断言必须亲手让它红一次」—— 同一件事。

## 十二、一个红灯需要绿灯来解释

「测试红了」本身信息量不足。可能是被测代码有 bug，也可能是测试前提就不成立（模型没加载、物体名写错、函数根本没被调用）。

Day 3 的三条测试构成完整判据：

| 测试 | 锁定的契约 | 缺了它会怎样 |
|---|---|---|
| 同 seed → 同结果 | **确定性** | 核心缺陷不可见 |
| 异 seed → 异结果 | **seed 有区分力** | 「seed 写死」的假修复能溜过 |
| 随机化确实发生 | **前提** | 前两条的绿可能是平凡解 |

**配一组「前提校验」测试，就能把红灯的含义收窄到唯一解释。**

这是 Day 2「找独立第二信源」的具体实现。

### 推论：失败信息里不要断言唯一根因

原来写的是：

> "随机化很可能根本没有执行，上一条测试的绿灯是平凡解"

自检 2 时它**指错了方向**（真实原因是 seed 被硬编码）。

**正确写法是列出可能性 + 指出如何区分**：

```
两种可能：
  (a) 随机化根本没执行 —— 若 test_randomization_actually_moves_objects 为绿则排除
  (b) seed 被硬编码/忽略 —— 更可能
```

## 十三、测试金字塔最容易漏的是「接线」

单元测试测每个零件，端到端测试测整机，**中间那层「零件怎么装到一起」最容易没人测**。

而现实缺陷大量集中在接线处：

| 缺陷 | 性质 |
|---|---|
| J（`collision_radius` 键名不匹配） | 配置与代码的接线 |
| seed 断链 | 配置层与代码层的接线 |
| Day 2 缺陷 B（模板缺 `observation` 段） | 模板与继承者的接线 |
| **缺陷 S**（贴图随机源） | **模块与模块的接线（import 边界）** |

**组件都对，装起来不工作** —— 集成缺陷的标准形态。

变异测试实测印证：「task_base 不传 seed」这个注入，**只有接线测试抓得到**，其他 3 条全绿。

## 十四、xfail 是一种诚实

| | `skip` | `xfail` |
|---|---|---|
| 含义 | 「**前提不满足，无法判断**」 | 「**断言应成立，但因已知缺陷不成立**」 |
| 用于 | 缺依赖、缺文件、平台不支持 | 已知 bug 尚未修复 |

**混用会把缺陷伪装成环境问题。** 三个月后有人看到 skip，会以为「这台机器不支持」，而不是「这里有个 bug」。

### `strict=True` 是关键

| | 缺陷仍在 | **缺陷被修好** |
|---|---|---|
| `strict=False`（默认） | XFAIL ✅ | **XPASS，静默通过** ⚠️ |
| **`strict=True`** | XFAIL ✅ | **XPASS 报为 FAILED** ✅ |

实测验证过两种情形。

**核心思想：让「缺陷已修复」也不会静默发生。** 状态变化必须被看见 —— 和这两天反复遇到的「静默是最大的敌人」是同一条。

### 对比 TODO 注释

| | TODO 注释 | `xfail(strict=True)` |
|---|---|---|
| 会被执行 | ❌ | ✅ 每次 CI |
| 修好了会怎样 | 没人知道，注释永远留着 | 强制有人回来撤标记 |
| 三个月后还准确吗 | 不知道 | 测试保证 |

## 十五、修复顺序按「相互干扰」排，不只按严重度

缺陷 J 插队到 seed 修复之前，**不是因为它更严重**，而是因为它会污染 Step 4 的验证：

```
碰撞半径不对 → 物体重叠判定不对 → 重试次数不对 → 随机数消耗次数不对
```

修完 seed 去跑测试，看到的是「seed 已修 + J 未修」的**叠加结果**。

**一次只改一个变量** —— 实验科学的基本功。这也是为什么分两次 commit：`git bisect` 只有在一个 commit 做一件事时才有用。

**事后验证**：修 J 并没有顺带修好 seed，两个缺陷确实独立。插队是为了**验证隔离**，不是因为有因果关系。

## 十六、批量替换的风险

`sed -i 's/np\.random\./self.rng./g'` 误伤了五分钟前刚写的 `self.rng = np.random.default_rng(seed)`。

### 三条教训

1. **批量替换会作用于「我刚写的新代码」** —— 改动顺序影响结果
2. **`sed -i` 敢用的唯一理由是代码已 commit** —— 版本控制是重构的安全网
3. **批量操作后先看 `git diff`**，别直接跑测试

### 顺带：这次的表现形式很典型

`__init__` 炸 → 第 2、3 条测试红。而第 1 条**仍然是红的，但病因换了**（从「seed 未生效」变成「构造函数崩溃」）。

**如果一口气改完三步再跑，这个病因切换根本不会被注意到。** → 每步跑一次测试的价值。

## 十七、覆盖率会「外溢」，但外溢的质量低

`mink_solver.py` 从 19% 涨到 46%，**我们一行都没测它** —— 是接线测试构造 `UniversalTaskBase` 时顺带跑到的。

**代码被执行过 ≠ 行为被验证过。**

Day 2 方法论第 10 条的延伸：覆盖率是下限指标，看 Missing 那列找盲区，不要盯总百分比。**尤其不要为外溢出来的数字高兴。**

## 十八、Day 3 方法论清单

1. **一个测试只能有一个失败原因。** 选断言对象时优先考虑「红了能不能归因」。
2. **容差的判据是「理论上应该差多少」**，不是「差多少我能接受」。
3. **测试必须走用户走的入口。** 从错误的入口进去，测的是别人家的代码。
4. **未消费的配置是独立缺陷模式** —— 它把缺陷伪装成系统固有属性。
5. **seed 一个不等于 seed 全部。** 确定性的边界是整条调用链，不是单个文件。
6. **全局可变状态是测试的头号敌人**（fixture 作用域 → 全局 PRNG → CI 并行，同一条原则）。
7. **状态的「家」在哪一层是设计决策**：构造时 seed vs 每次调用 seed，不能混。
8. **新增可选参数的默认值必须等价于旧行为。**
9. **同样的取值模式，安全与否取决于下游怎么用。**
10. **「这段逻辑没法测」通常是设计信号**，不是测试技术不够。
11. **变异测试验证测试本身有效** —— 注入真实的修复失误，比随机改符号更聪明。
12. **一个红灯需要绿灯来解释。** 失败信息里不要断言唯一根因。
13. **测试金字塔最容易漏的是接线。** 组件都对，装起来不工作。
14. **xfail(strict=True) 让「缺陷已修复」也不会静默发生。**
15. **修复顺序按「相互干扰」排**，不只按严重度。
16. **批量替换会作用于我刚写的代码**；`sed -i` 的安全网是 commit。
17. **覆盖率会外溢，但外溢的质量低。**
