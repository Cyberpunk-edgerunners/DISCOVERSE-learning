## 一、Flake 是什么，为什么它在具身智能里有双重身份

**Flake = 同样的代码、同样的输入，有时通过有时失败的测试。**

| | 稳定失败 | **flake** |
|---|---|---|
| 能复现 | ✅ | 随机 |
| 能定位 | ✅ | 难 |
| 团队反应 | 去修 | **「再跑一次就好了」** |

**flake 真正的伤害不是那 25% 的失败，是它摧毁了测试的可信度。**

一旦养成「红了就重跑」的习惯，**真正的缺陷也会被重跑掩盖**。测试套件从「质量闸门」退化成「随机噪声发生器」。

### 第二重身份

本项目的 `universal_task_runtime.py` **不是测试脚本，是数据采集器**。跑一次 = 采一条轨迹。

> **flake 率 = 数据采集失败率 = 训练数据的偏斜程度。**

这条等式让 Day 5 从「测试稳定性分析」变成了「数据管道质量分析」—— 后者对具身智能岗位的说服力强得多。

## 二、样本量决定你能回答什么问题

跑 1 次得不到任何信息（成功率非 0 即 100）。跑 N 次的标准误 ≈ √(p(1−p)/N)：

| N | 95% 置信区间（p≈0.5） |
|---|---|
| 10 | ±27% |
| 20 | ±19% |
| **50** | **±12%** |
| 200 | ±6% |

**N=50 能区分「84%」和「40%」，不能区分「50%」和「56%」。**

### 实测印证

我跑 30 次得 **76.7%**，用户跑 30 次得 **63.3%**。差 13.4 个百分点 ≈ 1.6 个标准误，**完全在正常波动内**。

> 📌 **同一实验、同一代码、两人各跑 30 次，差 13 个百分点。**
>
> 如果只跑一次就写「成功率 63.3%」，那是**过度精确的假象** —— 报三位有效数字，而真实不确定性有 ±8%。
>
> **诚实的写法**：「约 70%（N=30，95% CI ±17%）」。

### 推论：哪些结论对样本量敏感

| 结论 | 稳固性 |
|---|---|
| 「成功率 63.3%」 | ❌ 脆弱，N=30 波动 ±8% |
| **「双峰分布，中间真空」** | ✅ 稳固，两次独立采样都出现 |
| **「失败时方块没被搬动」** | ✅ 稳固，机理性结论 |

**写报告时把稳固的结论放前面，脆弱的数字加上置信区间。**

**Day 2 学过定性版**：「9 个样本 5 对 4 错能定位缺陷，2 个样本 1 对 1 错无法判断」。这是它的定量版。

## 三、分桶：让数字变得可行动

**「成功率 48.8%」不可行动** —— 你不知道该修什么。

**分桶 = 按失败根因分类**，让数字变成行动指南。

| Bucket | 判据 | 该修什么 |
|---|---|---|
| 1 | 完成状态 < 10/10 | IK 容差、工作空间 |
| 2 | 10/10 但判据失败 | 抓取、接触参数 |
| 3 | 超时 | 死循环、超时保护 |
| **4** | **异常崩溃，无完成状态** | **配置（不是 flake）** |

**同样是 40% 成功率**：全是 B1 → IK 问题；全是 B2 → 抓取问题；全是 B4 → 一行配置。

> 📌 **可行动指标 vs 虚荣指标**
>
> 「成功率 41%」听起来精确，但不告诉你下一步做什么 —— **虚荣指标**。
> 「B1 占 30%，且集中在 panda/ur5e」直接指向工作空间 —— **可行动指标**。
>
> **产出一个数字前先问：知道了它我会做什么不同的事？** 答案是「没有」的话，那个数字不值得测。

## 四、⭐ 分桶的第一职责是剔除「不是 flake 的东西」

计划文档只列了三个桶。**实测存在第四类：配置错误导致的必然崩溃。**

```
Camera 'eye_arm' not found in the MJCF model.
❌ 运行时执行失败: The camera "eye_arm" does not exist.
```

`cover_cup` 对非 airbot_play 机器人 **100% 崩溃，零随机性**。

### 混进统计的后果

| | 含 BUCKET4 | 剔除后 |
|---|---|---|
| 成功率 | 41.1% | **48.8%** |
| 差 | — | **7.7 个百分点** |

而且热力图上那一行会**永远是黑的**，误导人去调 IK 容差 —— 真正的问题是一行配置。

> 📌 **「必然失败」和「随机失败」是两类东西，混在一起两个都看不清。**
>
> 前者要修，后者要分析。**统计随机性之前，先把确定性的东西剔出去。**

## 五、分布形状比均值更有信息量

BUCKET2 的最终距离：

```
成功组: 0.0018 ~ 0.0195   （均值 0.0088）
失败组: 0.1736 ~ 0.3714   （均值 0.2505）
中间 0.154 m 完全没有样本
```

**双峰，中间真空。**

| 如果是 | 意味着 |
|---|---|
| 单峰，0.05 附近密集 | 「差一点点」→ **调阈值/容差可能有用** |
| **双峰，中间真空** | **二元结局** → 排除「精度不够」类假设 |

**均值 0.0088 vs 0.2505 只告诉你「有差别」；双峰告诉你「是二元结局」。**

**看直方图，不要只看均值和标准差。**

## 六、能读事实的时候，不要用数字去推

追 BUCKET2 根因走了四步，前三步全是间接推断，第四步一条数据定案。

**第四步：直接读 MuJoCo 的接触数据**

```python
for i in range(d.ncon):              # 当前接触数量
    c = d.contact[i]
    b1, b2 = m.geom_bodyid[c.geom1], m.geom_bodyid[c.geom2]
```

```
seed=13 全程:  方块接触 = ['table']              ← 夹爪从未碰到
seed=2  抓取时: 方块接触 = ['left','right','table']
```

> 📌 **「末端离方块 8mm」只是标量** —— 你不知道那 8mm 偏在哪、够不够得着。
> **「有没有接触」是布尔事实**，由物理引擎判定，不需要解释。
>
> **排查前先问：这个系统有没有直接暴露我要的事实？**

## 七、⭐⭐ 成对对比是最容易产生假根因的方法

**本日最重要的一课，而且是我犯的错。**

### 我的推理链

| | seed=2（成功） | seed=13（失败） |
|---|---|---|
| 横向偏差 | 7.9mm | 1.5mm |
| **轴向偏差** | 4.1mm | **8.1mm** |

结论：「方块在夹爪够不到的深度上，根因彻底查清了。」

**这个解释看起来完美** —— 同时解释了「总距离相近却结果相反」和「接触列表里从没出现手指」。

### 扩大到 20 个 seed 后

| seed | 轴向 | 结果 |
|---|---|---|
| 13 | 8.1mm | FAIL |
| **14** | **8.1mm** | **OK** ← 数值完全相同 |
| 4 | 7.5mm | OK |

四个候选变量的组间差异全在噪声范围内。**假设证伪。**

### 为什么会犯这个错

**任何两次运行之间都有几十个数值不同** —— 位置、高度、距离、角度、时序。你总能找到一个「看起来像原因」的，而且**它必然能解释这两个样本**（因为你就是从它们身上挑出来的）。

**统计上叫过拟合到样本：解释力 100%，泛化能力 0。**

### 唯一的解药

**主动去找反例** —— 不是等它出现，是**扩大样本专门去找**。

### 最讽刺的部分

我在 Day 5 tutorial §2.4 亲手写下过：

> 「两个样本的某个数值不同」不等于「那就是原因」—— 必须看整体分布。

**然后在下一轮里违反了它。**

> 📌 **知道一条原则，和在压力下遵守它，是两件事。**
>
> 找到「完美解释」的瞬间是最危险的 —— 那种「终于搞定了」的感觉会让你停止验证。
>
> **越是觉得自己找到了答案，越要去找反例。**

## 八、「根因未确定」是诚实的结论，不是失败

修正后的结论不写「根因是 X」，而是**分层**：

| 层级 | 内容 |
|---|---|
| **已排除** | IK（0.5mm，优于成功组）、手臂到位（8.3mm，优于成功组） |
| **已确认** | 夹爪闭合时与方块零接触 |
| **已证伪** | 轴向深度假设、桌面高度假设 |
| **弱相关** | 离基座 >0.315m（必要不充分） |
| **未确定** | 根因 |

> 📌 **一份「排除了 A、B，证伪了 C、D，锁定在 E 范围内」的报告，比一份自信的错误结论有价值得多。**
>
> 后者会让下一个人朝错误方向修 —— **负价值**。

### 单变量证伪也有局限

桌面高度假设被「按 z 排序无阈值」证伪。**但这个证伪方式本身有局限**：

**「单变量无关」≠「该变量不参与」** —— 它可能只在与其他变量组合时起作用（交互效应）。

前者是数据支持的，后者不是。

## 九、相关性的正确表述方式

| block 离基座 | 样本 | BUCKET2 失败 |
|---|---|---|
| < 0.315 m | 11 | **0** |
| ≥ 0.315 m | 19 | 10（53%） |

❌ 「因为太远所以失败」
✅ 「失败集中在 >0.315m 区域（10/19 vs 0/11），但该区域也有 **47% 成功** —— 距离是**风险因子**，不是**充分原因**」

**第二种更长更啰嗦，但它是对的，而且读者能据此判断该不该采信。**

## 十、确定性的三重价值（Day 3-4 修 seed 的回报）

Day 3 修 seed 时给的理由是「可复现性」。Day 5 兑现了三个具体收益：

### 价值 1：失败可精确复现

```
seed=42 → 8 次全部 0.0024
seed=13 → 5 次全部 0.2378（稳定失败）
```

**flake 从随机噩梦变成可复现缺陷。** 可复现的 bug 比不可复现的容易一个数量级 —— 能单步调试、能反复观测、修完能验证。

**这是本次能深入到接触层面的前提。**

### 价值 2：可以定向验证测试代码的每条分支

10 次自然采样只撞到 SUCCESS 和 BUCKET1，**BUCKET2 分支从未被执行过**（可能有 bug 而不自知）。

用 `seed=13` **定向制造** BUCKET2 → 三条全部 `dist=0.2378`，分支验证通过。

> **这是「代码覆盖率」思维应用在测试基础设施上。**
> 没有确定性的话，只能反复跑、祈祷撞上。

### 价值 3：让「不存失败数据」从有损变成廉价

有了 seed，**失败可精确重放** —— 存 32 字节的 seed 就够了，不必存 500MB 轨迹。

## 十一、⭐ flake 率 = 训练数据的偏斜程度

### 失败的运行被静默删除

```python
if not self.success:
    shutil.rmtree(self.save_dir, ignore_errors=True)
```

**对模仿学习这是正确的**：

| 用途 | 要失败数据吗 |
|---|---|
| 行为克隆 / 模仿学习（ACT/DP/RDT） | ❌ 失败轨迹不是专家行为，会直接学错 |
| 强化学习（PPO） | ✅ 负奖励是学习信号 |
| 失败检测器 / 价值函数 | ✅ 没负样本没法训 |

### 但代价一：幸存者偏差

失败**集中在离基座较远的区域**。删除后：

- 近距离样本：全部保留
- 远距离样本：**只留下碰巧成功的那一半**

**训练集的空间分布被系统性扭曲。策略在远处更差，而指标上看不出来** —— 因为验证集同样偏斜。

> 二战时统计返航飞机的弹孔分布，想给弹孔多的位置加装甲。Wald 指出应加在**没有弹孔**的位置 —— 被击中那里的飞机根本没飞回来。
>
> **数据集是「飞回来的飞机」。缺失的样本携带最重要的信息。**

### 代价二：失败率本身是被丢掉的质量信号

删除是静默的：无日志、无计数。于是不知道采集 100 条实际尝试了多少次、失败集中在哪。

**「51% 的尝试失败了」本身就是关于任务设计的关键信息。**

### 建议：三级保留策略

| 级别 | 内容 | 用途 |
|---|---|---|
| L1 | 成功轨迹（完整） | IL 训练 |
| **L2** | **失败元数据**（seed、位姿、分桶、距离） | **分析、复现、覆盖率** |
| L3 | 失败完整轨迹 | RL、失败检测器 |

**L2 每条几百字节，性价比最高。**

## 十二、区分「回归测试」和「实验」

| | 回归测试 | **实验** |
|---|---|---|
| 目的 | **守住**已知正确行为 | **测量**未知的量 |
| 频率 | 每次提交 | 偶尔 |
| 耗时 | 秒级 | 分钟~小时 |
| 有断言吗 | 必须有 | **可以没有** |
| 结论 | 通过/失败 | 数字 + 置信区间 |
| 失败意味着 | **有人改坏了** | 可能只是采样波动 |

**混在一起：回归被拖垮（3 秒 → 81 分钟），且实验的「失败」会被误读成「代码坏了」。**

隔离手段是 **marker + 默认排除**：

```toml
addopts = "... -m 'not flake'"
```

验证生效：`113 passed, 45 deselected in 3.04s`。

### 推论：采样器不该有成功断言

45 个组合一大半会永远红，测试就失去意义了。

**唯一的断言是「不能是 BUCKET4」** —— 那是确定性缺陷，应该被修，不该被当成 flake 容忍。

## 十三、对采样器来说，「passed」几乎没有信息量

小规模验证得到 `5 passed`，**但这不能说明分桶对了** —— 测试只在 BUCKET4 时 fail。

- 5 次全成功 → PASSED
- 5 次全是 BUCKET2 → **也是 PASSED**

**必须去看 `record_property` 记了什么。验证产出，不是验证退出码。**

> 📌 **这和 Day 2 方法论第 3 条（「CI 判定必须基于退出码」）看似矛盾，其实是两类东西：**
>
> | | 结论在哪 |
> |---|---|
> | 回归测试 | **退出码** |
> | 实验/采样器 | **数据里**（退出码只说明「跑完了」） |

## 十四、序列化会改变数据结构

```python
dict(t.get("user_properties", []))
# ValueError: dictionary update sequence element #0 has length 1; 2 is required
```

**真实结构**：

```python
[{'robot': 'airbot_play'}, {'bucket': 'SUCCESS'}]   # 一串单键字典
```

`record_property("robot", "x")` 在**内存里**是元组，导出 JSON 时变成了 `{"robot": "x"}` —— **JSON 没有元组类型**。

> 📌 **不要假设导出格式和内存格式一致。**
> 第一次接触任何序列化产物，先 `print(repr(...))` 看真实结构。

## 十五、可视化里「缺失」和「零」必须能被区分

`cover_cup` 那行有 4 格是 100% 配置崩溃 → `rate` 为 NaN → `imshow` 默认画成**白色**。

**白色会被误读为「没测试」，而实际是「测了，每次都崩」。**

```python
cmap = plt.get_cmap("RdYlGn").copy()
cmap.set_bad("#9e9e9e")                       # NaN 染灰
im = ax.imshow(np.ma.masked_invalid(rate), cmap=cmap, ...)
```

**那几格恰恰是最需要被看见的。**

### 顺带：图不是为了好看

| | 适合 |
|---|---|
| 表格 | 查具体数值 |
| **图** | **发现结构** |

扫表格要几秒才看出「cover_cup 整行是 0」，画成图后那一行是纯色的，零点几秒就看到。

## 十六、实验产出物是资产，不是临时文件

`/tmp/flake.json` 重启就没了。**2250 次运行 = 10 分钟 + 等待成本**，这个数据应该被保存。

工业界叫 **artifact（制品）**。CI 专门有「上传 artifact」这一步，原因是：**运行是昂贵的，结果是廉价的，不要为了看结果而重新运行。**

### 该存 vs 不该存

| 该存 | 不该存 |
|---|---|
| 小（<1MB） | 大（视频、模型权重） |
| **是结论的证据** | 中间产物 |
| **难以重新生成** | 一条命令就能重来 |

**本次 CSV 四条全中**；对比 `data/` 目录（任务采集的视频轨迹）—— 大、每次跑都变、是中间产物，**所以上游把它加进 `.gitignore` 是对的**。

### 「暂存」和「随便存」的区别

```yaml
retention:
  rationale: 155KB 换「结论可复算」。数据含随机性，重跑得不到同一份。
  exit_condition: 累积约 10 份实验（~1.5MB）时迁 Git LFS 或 CI artifact。
```

> 📌 **没有退出条件的临时方案，三年后还在，而且没人敢动** —— 因为不知道当初为什么这么做。
>
> **写下「什么时候该换」，比写下「为什么这么做」更有用。**

### 元数据必须带「产生它的条件」

```yaml
git_commit: c722ca8ae0d9bb2d8c4b16df20c6d879f315b161
caveats:
  - BUCKET4 是配置缺陷…统计 flake 率时必须剔除
  - N=50 时 95% CI 约 ±12%，不要用它区分接近的数值
```

**`git_commit` 那行最重要** —— 三周后能知道数据是在哪个版本上跑的。没有它，数据就是孤儿。

**caveats 不是免责声明，是使用说明** —— 否则半年后拿到 CSV 的人会直接算 924/2250=41%，得到一个被稀释的错误数字。

## 十七、`.gitignore` 的模式匹配

| 写法 | 匹配范围 |
|---|---|
| `data` | **任意层级**的 data 文件或目录 |
| `/data` | **仅根目录** |
| `data/` | 任意层级的 data **目录**（不匹配文件） |

上游写的是 `data`（最宽的一种），所以 `docs/data/` 也中招。

**`git check-ignore -v <文件>` 会告诉你是哪一行挡的** —— 比猜快得多。

## 十八、渲染后端与实时同步

看画面调试时的两个开关：

| `MUJOCO_GL` | 用途 |
|---|---|
| `osmesa` | 软件离屏，**无显示器**（CI、Docker） |
| `glfw` | **开窗口** |
| `egl` | GPU 加速离屏 |

`env.sh` 写死了 `osmesa`（为 CI 准备），看画面要 `export MUJOCO_GL=glfw`。

**加 `-s`（`--sync`）**：不加的话仿真快放 15 倍（0.22s 跑完 3.45s 的仿真），窗口一闪而过。

> 📌 **可视化在调试里的定位**：不能替代量化分析（没法看 30 次然后统计），但对**形成假设**极其高效。
>
> **正确顺序：可视化建立直觉 → 量化验证直觉。**

## 十九、Day 5 方法论清单

1. **flake 的伤害不是失败率，是它摧毁测试的可信度。**
2. **在具身智能里，flake 率 = 训练数据的偏斜程度。**
3. **样本量决定你能回答什么问题。** 做实验前先问：要区分多大的差异？
4. **同一实验两人各跑 30 次可差 13 个百分点** —— 不要报过度精确的数字。
5. **区分稳固结论和脆弱数字**，前者放前面，后者加置信区间。
6. **分桶让数字可行动**：产出数字前先问「知道了它我会做什么不同的事」。
7. ⭐ **分桶的第一职责是剔除「不是 flake 的东西」。** 统计随机性前先剔除确定性。
8. **分布形状比均值更有信息量。** 双峰 = 二元结局，直接排除「精度不够」类假设。
9. **能读事实的时候不要用数字去推。** 先问系统有没有直接暴露该事实。
10. ⭐⭐ **成对对比是最容易产生假根因的方法** —— 过拟合到样本，解释力 100%、泛化 0。
11. ⭐ **越是觉得找到了答案，越要主动找反例。**
12. ⭐ **知道一条原则，和在压力下遵守它，是两件事。**
13. **「根因未确定」是诚实的结论。** 分层结论比自信的错误结论有价值。
14. **「单变量无关」≠「该变量不参与」**（交互效应）。
15. **相关性要标注强度**：「风险因子」而非「充分原因」。
16. **确定性的三重价值**：失败可复现、可定向验证测试分支、让不存失败数据变廉价。
17. **区分「回归测试」和「实验」**，marker + 默认排除。
18. **采样器不该有成功断言**；对它来说「passed」几乎没有信息量。
19. **不要假设导出格式和内存格式一致。**
20. **可视化里「缺失」和「零」必须能被区分。**
21. **实验产出物是资产**：运行昂贵、结果廉价，不要为了看结果而重跑。
22. **「暂存」要写下退出条件**，否则三年后还在且没人敢动。
23. **实验数据必须带产生它的条件**（git commit + caveats）。
