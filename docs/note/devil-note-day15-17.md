## 一、⭐ 核心认知：仿真里最容易错的是「描述物理的常数」

物理引擎本身很难错 —— MuJoCo 的积分器、接触求解器都是被反复验证过的。
**容易错的是喂给它、或从它旁边拿来用的那些常数。**

今天抓到的缺陷 Y 是标本：

```python
# discoverse/robots_env/mmk2_base.py:63
wheel_distance = 0.189        # MJCF 实测 0.3265，错 1.73 倍
```

### 为什么常数错误特别难抓

| 代码错误 | 常数错误 |
|---|---|
| 抛异常、崩溃、返回 None | **静默给出一个看起来合理的数** |
| 有堆栈可以定位 | 没有任何痕迹 |
| 单测容易覆盖 | **需要外部真值才能发现** |

`wheel_distance` 错了 73%，但推算出来的位姿**始终是一个合法的三元组**，
永远不会 NaN、不会越界、不会报错。

### ⭐ 判断标准

> **凡是「代码里写死的物理量」，都要问一句：它和模型里的那个是同一个吗？**

今天的做法是**从 MJCF 现算**，不引用被测常量：

```python
# tests/mobile_manipulation/conftest.py
ys = [model.body_pos[model.jnt_bodyid[jid]][1] for jid in wheel_joints]
wheel_distance = abs(ys[0] - ys[1])       # 实测 0.3265
```

📌 **测试若引用被测常量，就无法证伪该常量。**这是本目录最重要的一条设计原则。

## 二、⭐⭐ 空转测试：比红测试危险得多

### 2.1 三种形态，今天全遇到了

| 形态 | 今天的实例 | 为什么恒真 |
|---|---|---|
| **匹配一个不存在的东西** | `if "left_arm" in geom1` | 62/73 个 geom 无名，`in ''` 恒 False |
| **除以一个恒为 0 的分母** | `abs(d[0])/abs(d[1])` | 机器人沿 +x 走，y ≈ 0 |
| **在恒等变换下测试** | 底盘永远在原点 | world 系与 footprint 系数值上恰好相等 |

三种的共同点：**测试是绿的，而且看起来在测东西。**

### 2.2 为什么它比红测试危险

```
红测试  → 有人看 → 要么修代码要么改测试 → 总之会被处理
空转测试 → 没人看 → 制造「这块有覆盖」的错觉 → 真出问题时无人预警
```

⚠️ **空转测试还会污染覆盖率数字** —— 那行代码确实被执行过，
`coverage` 会把它算成已覆盖，但断言什么都没验证。

### 2.3 ⭐ 通用解法：让测试先失败一次

> **一个从未红过的测试，你不知道它会不会红。**

三种具体手法（今天都用了）：

**① 元测试** —— 先构造必然失败的场景，断言它被检出

```python
def test_self_collision_detector_actually_detects():
    """已知碰撞位形必须被检出。它是「安全位形无碰撞」那条测试的前提。"""
    hits = pose_arms(model, data, POSE_COLLIDING, POSE_COLLIDING)
    assert hits, "检测器失效：已知碰撞位形却报告无跨臂接触"
```

**② 前置断言** —— 凡是「比值 < 阈值」，必先断言分母足够大

```python
assert longitudinal > 0.1, "机器人几乎没有前进，直线度测试无意义"
straightness = lateral / longitudinal
```

**③ 变异测试** —— 把实现改坏，看测试红不红

```
把 world_to_footprint 改成不做变换：
→ 1 failed, 11 passed
→ 只有「底盘非原点」那条抓得到；另外 11 条对坐标系错误完全无感
```

📌 **变异测试是元测试的通用形式。**成本：改一行、跑一次、改回来，不到一分钟。
收益：把「我觉得这测试有用」变成「我验证过它有用」。

## 三、⭐⭐ 恒等陷阱：在特例下测试，通过了也没意义

### 3.1 机制

```
FK 返回 world 系位姿  ─┐
                      ├─ 底盘在原点且无旋转时，两者【数值上恰好相等】
IK 需要 footprint 系  ─┘
```

于是「忘记做坐标变换」的实现，在原点下**完美通过**往返测试。
一旦底盘移动，同样的代码要么静默给出错误答案，要么误报不可达。

### 3.2 这类陷阱的一般形式

**当两个本该不同的东西，在某个特殊输入下恰好相同时，
用那个输入做的测试，无法区分「实现正确」和「实现遗漏」。**

常见的「恒等输入」：

| 领域 | 危险的默认值 |
|---|---|
| 坐标变换 | 原点、单位四元数、单位矩阵 |
| 工业机器人标定 | TCP = 0、工件坐标系 = 基坐标系 |
| 缩放/归一化 | scale = 1.0 |
| 时序 | dt = 1.0 |
| 偏移 | offset = 0 |

📌 **写测试时刻意避开这些值。**今天的做法：专门写一条
`test_roundtrip_with_base_off_origin`，底盘同时**平移 + 旋转 90°**。

变异测试证明了它的价值 —— **它是 12 条用例里唯一抓得到坐标系错误的一条。**

## 四、⭐ 误差的结构比误差的大小更有信息量

### 4.1 实例：6.06mm 该不该判缺陷？

```
target= 0.000  →  err= 0.006063
target= 0.200  →  err= 0.006063
target= 0.500  →  err= 0.006063
target=-0.040  →  err= 0.006063
target= 0.870  →  err= 0.000399      ← 撞关节上限
```

计划文档的容差是 5mm，**实测 6.06mm，超了**。

但只看「6.06 > 5」会得出错误结论。看**结构**：

| 观察 | 推论 |
|---|---|
| 各目标位误差**六位小数相同** | 不是随机噪声，是**系统偏置** |
| 符号**恒为正** | 有方向性 → 有物理成因 |
| 结合「slide 越大躯干越低」 | 正偏置 = 躯干比目标低 = **重力** |
| `<position>` 是比例控制器 | 稳态必须留偏差产生抗重力的力：`err = 负载 / kp` |

→ **结论：位置伺服的固有下垂（droop），不是缺陷。**真机上也一样。

### 4.2 ⭐ 于是有了一条更好的断言

不是简单放宽容差，而是：

```python
# ① 定位精度（实测 6.06mm，取 10mm）
assert abs(actual - target) < 0.010

# ② ⭐ 下垂偏置的一致性 —— 抓「精度」抓不到的故障
assert np.ptp(errors) < 1e-4, f"各高度下垂不一致，可能存在卡滞：{errors}"
```

第 ② 条的价值：**重力下垂应当处处相同；某个高度突然不一样 = 卡滞/干涉。**
这是「误差 < 10mm」永远抓不到的故障模式。

### 4.3 一般化

> **面对一个超标的数字，先问「它是什么形状的」，再问「它有多大」。**

| 误差形状 | 指向 |
|---|---|
| 恒定偏置 | 标定参数、伺服增益、坐标系原点 |
| 随比例增长 | 缩放因子、单位换算 |
| 随机抖动 | 噪声、时序、并发 |
| 只在某工况出现 | **该工况暴露了某个平时被乘以 0 的项** |

最后一行正是缺陷 Y：**直线时轮距被乘以 0，所以只有转弯才暴露。**

## 五、⭐ 「被乘以 0 的项」：为什么标定必须选对工况

差速里程计：

```
Δθ = (Δs_right - Δs_left) / L
```

**直线行驶时 `Δs_right - Δs_left = 0`** → 整项为 0 → **L 错得再离谱都不影响结果**。

实测印证：

| 工况 | yaw 误差（用错误的 L=0.189） |
|---|---|
| 直线 | 0.0005 rad ← 几乎完美 |
| 缓转弯 | 0.5584 rad |
| 原地旋转 | **1.9440 rad（111°）** |

📌 **工业 AGV 的常识：轮距标定必须用原地旋转，不能用直线跑。**
今天把它写成了一条测试（`test_straight_line_hides_wheel_distance_error`），
**用来解释 xfail 的存在理由**。

### 一般化

> **参数标定的工况选择，等价于「让待测参数的系数最大化」。**

写测试时同理：**要验证参数 P，就构造让 P 的影响最大的输入。**
反过来说 —— **如果一个测试对某参数不敏感，它就不能用来验证该参数。**

## 六、语义歧义：为什么「只改数值」是危险的修法

发现 `wheel_distance = 0.189` 错了，最自然的动作是改成 `0.3265`。**不能这么干。**

```bash
grep -rn "wheel_distance" --include=*.py .
```

两处用法**互相矛盾**：

```python
# 里程计（今天写的）—— 按【全轮距】用
Δθ = (Δs_r - Δs_l) / L

# examples/ros{1,2}/*.py —— 按【半轮距】用（少除以 2）
v_left = (v - ω * wheel_distance) / wheel_radius
#              ↑ 标准公式应是 ω * L / 2
```

所以：

| 取值 | 里程计 | ROS 遥操作 |
|---|---|---|
| 0.189（现状） | 错 73% | 错 15.7% |
| 0.3265（"修正"） | ✅ 对 | **错 100%** |

> ⭐ **一个变量被两处按不同语义使用时，没有任何单一取值是对的。**
> 修法必须先**消除歧义**（重命名为 `wheel_base` / `half_wheel_base`），再统一取值。

📌 **今天的处理：`xfail` 钉住 + 缺陷报告登记 + 明确写下「为什么不修」。**
「发现了但故意不修，并说清楚原因」比「顺手改了个数」专业得多。

## 七、⭐ 结构比命名可靠

geom 名字缺失（62/73 无名）时，改用 **body 父子关系**做归属判断：

```python
def arm_side(model, geom_id):
    for name in body_chain(model, model.geom_bodyid[geom_id]):
        if name.startswith(("lft_arm", "lft_finger")): return "L"
        if name.startswith(("rgt_arm", "rgt_finger")): return "R"
    return None
```

| | 可靠性 |
|---|---|
| **命名** | 靠人自觉，可缺失、可拼错、可不一致 |
| **结构**（父子关系、拓扑） | 由物理模型强制，不写就建不出模型 |

> **当直接的标识不可用时，往结构里找。**

⚠️ 但要**为这个判断本身写测试** —— 我加了
`test_arm_side_resolves_unnamed_geoms`，断言「确实有**无名** geom 被成功归属」，
否则方案会悄悄退化成「按名字匹配」（那 11 个有名 geom 仍能匹配上，
测试看起来还是绿的）。

## 八、⭐⭐ 「没测就写」：四次自我打脸的共同形态

今天有 4 处是我凭直觉写下、事后被实测推翻的：

| 我以为 | 实测 | 危害 |
|---|---|---|
| `mj_resetData` 后四元数要手动补 | 不用补 | 多余代码 + **错误的解释传给读者** |
| 模型加载 1 秒 | 0.14 秒 | 用假数字论证设计决策 |
| 测试合计 55 秒 | 6 秒 | **差点把缺陷挪出 CI 主线** |
| 重叠率随网格失真 | 比值很稳定 | 理由错了但结论对 —— **最难自查** |

### 8.1 共同点：四个都不会报错

```
多余的赋值        → 无害
过大的 fixture scope → 无害
slow 标记         → 不会让任何测试变红
写错的理由        → 连代码都不碰
```

📌 **它们的代价不是失败，是让你以为自己验证过了。**

### 8.2 ⭐ 最危险的是第 4 种：理由错了但结论对

我说「重叠率随网格步长失真，所以不该写成断言」——
**结论正确**（确实不该写成断言），**理由错误**（比值其实很稳定）。

这种最难自查，因为**结果看起来没问题，没有任何东西会提醒你回头**。

实测之后才找到真正的理由，而且**硬得多**：

```
「重叠/单臂」 44.9~48.4%  → 远超 30%，阈值形同虚设
「重叠/并集」 29.0~31.8%  → 骑在 30% 线上
                step=0.15 → 29.0% 失败
                step=0.06 → 31.8% 通过
```

**红绿取决于测试自己的参数，不取决于机器人有没有问题。**

> ⭐ **这是一种 flaky 断言，但随机源不是时序或并发 ——
> 是测试作者自己选的一个常数。**

Day 5 量化 flake 时随机源是仿真本身；今天这个更隐蔽。

### 8.3 教训

> **性能优化、容差、阈值 —— 这三样东西的每一个数字都必须来自测量。**
> 拍脑袋定的容差要么天天红（噪声），要么什么都抓不到（空转）。

## 十、拒绝实现一个测试，也是产出

计划文档要求写「工作空间重叠率 > 30%」的断言。**我没写**，改成度量脚本，理由：

1. **阈值没有出处**（"> 30%" 是拍的）
2. ⭐ **分母口径未定义时，阈值可以被「选」成任何结论**（48% vs 31%）
3. ⭐ **在关键口径下，结论对采样分辨率敏感** —— flaky 断言
4. **它测的是几何不是行为**，MJCF 不变就不会变红
5. 成本高（0.06 步长 5292 点需数分钟）

> ⭐ **「能写」不等于「该写」。**
> 一个阈值拍脑袋、口径未定义、且红绿取决于自身参数的测试，是**纯负债**：
> 消耗 CI 时间，制造虚假的覆盖率信心，红了没人知道怎么办。

📌 **替代方案不是「不做」，是「降级为度量」** ——
`scripts/mmk2_workspace_overlap.py` 输出三个口径的数字供人看，
明确声明不做阈值判定。等有明确需求再决定要不要变成断言。

## 十一、不为想象中的需求扩接口

Day 13-14 的 `FailureMode.ALL` 目前是
`ik_early / final_check / timeout / config / crash`。

移动操作显然需要更多类别（`base_pose` / `slide_range` / `self_collision`）。
**但今天没加。**

理由：契约有一条不变式「`failure_mode` 必须在 `ALL` 内，拼错当场炸」。
加类别是**扩展契约**，应该等到**真有 MMK2 任务在跑并产出这些失败**时再加。

> **在没有消费者的时候扩接口，等于用契约的严格性去背书一个还没验证的分类法。**

→ 只在 checkpoint 里记下提案。

## 十二、一句话总结

> **仿真里最容易错的不是物理，是那些「描述物理的常数」。
> 因为常数不会崩溃、不会抛异常、不会在直线上暴露 ——
> 它只在你转弯的时候，悄悄把 111 度当成 152 度告诉你。**

配套的一句：

> **而验证这类错误的唯一办法，是让测试先失败一次 ——
> 元测试、前置断言、变异测试，三者都是同一件事的不同形式。**
