## 第 0 章 总论：黑盒测试方法论

### 0.1 核心命题

> **测试的价值不在于能不能看源码，而在于能不能从使用者视角发现开发者的盲区。**

看得到源码是"白盒的便利"，看不到源码是"工业界的常态"。成熟的测试开发思维必须能在**任意可见性层级**下工作。

### 0.2 可见性层级（Visibility Ladder）

拿到一个被测组件，第一件事是判断它处在哪一层——这决定你能用什么手段。

| 层级 | 你拿到的 | 可见性 | 主要手段 |
|---|---|---|---|
| **L4 全源码** | `.c/.cpp/.py` 全部 | 白盒 | 读码定位、覆盖率、单元测试、静态分析 |
| **L3 源码+头文件** | 头文件 + 部分源码 | 灰盒 | 接口契约 + 部分白盒 |
| **L2 库+头文件** | `.so/.a/.lib` + `.h` | 灰盒（接口可见） | 契约测试、符号表、动态追踪 |
| **L1 纯二进制** | 只有 `.so/.o`，无头文件 | 黑盒 | 逆向符号表、反汇编、fuzzing |
| **L0 固件/黑盒设备** | 烧录好的控制器、示教器整机 | 全黑盒 | 协议嗅探、硬件在环、录制回放 |

**关键认知**：工业机器人测试里，你几乎不会停在 L4。供应商的运动控制库通常是 L2/L1，控制器固件是 L0。**越往下走，"试探"和"对比"越重要，"阅读"越无力。**

### 0.3 三条黑盒测试主线

无论哪个模块，黑盒测试都落在这三条主线上：

```
主线一：契约测试（Contract Testing）
  把接口/协议规格当"合同"，验证被测方是否遵守。
  规格从哪来？头文件注释、协议文档、通讯手册、示教器操作手册。
  没有文档时，用符号表 + strings + 反汇编反推隐式契约。

主线二：异常与边界注入（Fault Injection）
  源码看不到内部边界，只能从外部穷举：空指针、越界值、非法状态、
  并发竞争、超时、断连、资源耗尽。黑盒下这条比白盒更重要——
  因为你无法从代码里读出边界，只能试出来。

主线三：差分/对比测试（Differential Testing）
  没有"正确答案"参照物时，制造一个：
  - 仿真 vs 真机（Sim2Real）
  - 新版本 vs 旧版本（回归）
  - 跨实现对比（A 厂库 vs B 厂库，同输入应同输出）
  - 数学不变量（FK∘IK=I，能量守恒，往返一致）
```

### 0.4 从二进制"读"出隐式规格

即使 L1 纯二进制，也不是完全瞎测。可提取的信息：

```bash
# 1. 导出符号——知道有哪些函数可调
nm -D librobot.so | grep " T "        # T = 已定义的导出函数
nm -DC librobot.so                    # -C 解 C++ name mangling

# 2. 依赖关系——知道它底层依赖什么
ldd librobot.so                       # 动态库依赖
readelf -d librobot.so | grep NEEDED  # 同上，更底层

# 3. 字符串——隐式文档金矿
strings librobot.so | grep -iE "error|assert|invalid|fail|out of|range"
# 常能挖到：
#   "assertion failed: joint_idx < 6"      → 关节数=6，索引边界
#   "IK target out of workspace"           → 有工作空间检查
#   "invalid quaternion norm: %f"          → 会校验四元数归一化
#   "CAN bus timeout after %d ms"          → 通讯超时机制

# 4. 符号信息（未 strip 时）看内部函数名
readelf -Ws librobot.so | awk '{print $8}' | grep -v UND | sort -u

# 5. 反编译成伪 C（需要 Ghidra/IDA）
#    Ghidra 开源免费，能把汇编还原成可读的伪代码，看清分支逻辑
```

> **这些字符串就是隐式文档。** 供应商没给你规格书，但编译进二进制的错误消息、断言、日志格式，泄露了它内部检查哪些条件——这些正是你该覆盖的边界。

### 0.5 通用降噪心法（贯穿全文）

黑盒测试会产生大量运行时输出（日志、抓包、trace）。抓重点的三条：

1. **带着问题看** —— 先立一个待验证的假设，只找回答它的部分，其余无视。
2. **聚合再看细节** —— `sort | uniq -c | sort -rn` 统计模式频率，异常往往是低频离群项。
3. **关注"缺失"而非"存在"** —— 该出现的心跳帧没出现、该有的 ACK 没回、日志里该报的错被吞了——**"本该有却没有"比"有什么"信息量更大**。

## 第 1 章 实时 / 非实时通讯

### 1.1 被测对象与典型形态

**被测对象**：
- **实时通讯**：EtherCAT、CANopen、PROFINET RT、Modbus RTU —— 硬实时，周期性，微秒级延迟敏感
- **非实时通讯**：TCP/IP（Modbus TCP、OPC UA）、串口、CAN 2.0B —— 允许毫秒级抖动，有重传机制

**拿到的形态**：
- **L2 级**：供应商提供 `.so` + 头文件（如 SOEM 库、CANopen SDK）
- **L1 级**：控制器烧录了固件，只通过 CAN/EtherCAT 总线对外通讯，没有 API
- **L0 级**：黑盒电机驱动器，只知道报文格式（PDO/SDO）

### 1.2 测试策略矩阵

| 维度 | 实时通讯（EtherCAT/CAN） | 非实时通讯（TCP/Modbus） |
|---|---|---|
| **契约测试** | 时序约束（周期抖动 <1ms）、CRC 校验、总线仲裁 | 超时重传、连接保活、错误码完整性 |
| **异常注入** | 丢包（拔电缆）、总线冲突、从站掉线、过载 | 断网、半连接、粘包、错序、超长包 |
| **性能基线** | 延迟分布（P50/P99）、CPU 时间片占用 | 吞吐量、并发连接数、重连风暴 |
| **专属测试** | 分布式时钟同步误差、DC Sync 精度 | 长连接泄漏、慢速客户端拖死服务端 |

### 1.3 实时通讯核心测试点

#### A. 周期性与抖动（Jitter）

**黑盒验证方法**：
```python
# 用示波器或逻辑分析仪抓总线波形，或用 Wireshark 抓包
import numpy as np
import pandas as pd

def test_cycle_time_jitter():
    """测量 EtherCAT 帧间隔，验证周期稳定性"""
    # 从 pcap 文件提取时间戳（Wireshark 导出）
    timestamps = pd.read_csv('ethercat_capture.csv')['timestamp'].values
    intervals = np.diff(timestamps) * 1000  # 转毫秒
    
    # 统计抖动
    mean_cycle = intervals.mean()
    jitter_p99 = np.percentile(intervals, 99)
    
    print(f"平均周期: {mean_cycle:.3f} ms")
    print(f"P99 抖动: {jitter_p99:.3f} ms")
    
    # 契约：1kHz 周期 = 1ms，抖动应 <50us
    assert abs(mean_cycle - 1.0) < 0.05, f"周期偏离: {mean_cycle}ms"
    assert jitter_p99 < 1.05, f"P99 抖动超标: {jitter_p99}ms"
```

**工具**：
- `tcpdump` + Wireshark 抓 EtherCAT 帧（需要特殊插件）
- Twincat Scope 录波（倍福系统）
- Saleae 逻辑分析仪（硬件工具，能看波形）

**真实案例讲法**：
> "钱江的 EtherCAT 主站是供应商闭源库。我用逻辑分析仪抓 1 分钟总线波形，导出时间戳后统计发现 P99 延迟 1.2ms，超出 1kHz 周期要求。通过对比负载不同时的抖动分布，定位是 CPU 调度问题——主站线程优先级不够，被其他任务抢占。反馈后供应商调整了线程优先级和 CPU 亲和性，P99 降到 1.03ms。"

#### B. 从站掉线与恢复

**测试用例**：
```python
def test_slave_dropout_recovery():
    """模拟 EtherCAT 从站掉线（拔电缆）"""
    master = EtherCATMaster()  # 闭源库的 Python binding
    master.start()
    
    # 1. 正常通讯
    for _ in range(100):
        master.send_process_data()
        time.sleep(0.001)
    assert master.get_slave_state(1) == "OPERATIONAL"
    
    # 2. 模拟掉线（物理拔电缆，或软件禁用网卡）
    input("请拔掉从站 1 的网线，按回车继续...")
    time.sleep(0.5)
    assert master.get_slave_state(1) == "OFFLINE"
    
    # 3. 恢复
    input("请重新插入网线，按回车继续...")
    time.sleep(2.0)
    
    # 契约：2 秒内应自动重连
    assert master.get_slave_state(1) == "OPERATIONAL", "未自动恢复"
    
    # 契约：恢复后数据应连续，无乱序
    data_after = master.read_input_data(1)
    assert data_after['counter'] > 0, "计数器未恢复"
```

**为什么这是黑盒的关键测试**：
- 供应商文档只写"支持热插拔"，没说恢复时间和数据完整性
- 源码看不到，只能用物理手段（拔电缆）真实触发
- 真实生产线上电缆松动是常态，必须验证

#### C. CAN 总线仲裁与优先级

**测试场景**：
```python
def test_can_arbitration():
    """验证 CAN 报文优先级（ID 越小优先级越高）"""
    import can
    
    bus = can.interface.Bus(channel='can0', bustype='socketcan')
    
    # 同时发送高优先级（ID=0x100）和低优先级（ID=0x700）
    msg_high = can.Message(arbitration_id=0x100, data=[1,2,3], is_extended_id=False)
    msg_low = can.Message(arbitration_id=0x700, data=[4,5,6], is_extended_id=False)
    
    # 并发发送，看谁先到
    bus.send(msg_low)
    bus.send(msg_high)
    
    # 接收方应先收到高优先级帧
    received = []
    for _ in range(2):
        msg = bus.recv(timeout=0.1)
        received.append(msg.arbitration_id)
    
    assert received == [0x100, 0x700], f"仲裁失败，实际顺序: {received}"
```

### 1.4 非实时通讯核心测试点

#### A. TCP 粘包与半包

**典型问题**：
```python
# 错误的读取方式（很多闭源库里有这个bug）
def buggy_read(sock):
    data = sock.recv(1024)  # 假设一次 recv 能拿到完整报文 ❌
    return parse_message(data)

# 正确方式：处理半包和粘包
def correct_read(sock, expected_length):
    buffer = b''
    while len(buffer) < expected_length:
        chunk = sock.recv(expected_length - len(buffer))
        if not chunk:
            raise ConnectionError("连接断开")
        buffer += chunk
    return parse_message(buffer)
```

**黑盒验证**：
```python
def test_tcp_fragmentation():
    """模拟网络拥塞，故意发送分片报文"""
    import socket
    
    server_addr = ('192.168.1.100', 502)  # Modbus TCP
    sock = socket.socket()
    sock.connect(server_addr)
    
    # 正常完整报文：6 字节头 + 数据
    request = b'\x00\x01\x00\x00\x00\x06\x01\x03\x00\x00\x00\x0A'
    
    # 故意分三次发送（模拟粘包）
    sock.sendall(request[:4])
    time.sleep(0.01)
    sock.sendall(request[4:8])
    time.sleep(0.01)
    sock.sendall(request[8:])
    
    # 服务端应能正确解析
    response = sock.recv(1024)
    assert len(response) > 0, "未响应（可能半包处理有bug）"
    assert response[7] == 0x03, "功能码错误"
```

#### B. 连接泄漏与资源耗尽

**测试用例**：
```python
def test_connection_leak():
    """并发打开大量连接，验证服务端是否泄漏"""
    import socket
    import threading
    
    def open_and_close():
        for _ in range(100):
            sock = socket.socket()
            sock.connect(('192.168.1.100', 502))
            sock.close()
    
    # 10 个线程并发
    threads = [threading.Thread(target=open_and_close) for _ in range(10)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    
    # 检查服务端是否还能响应（泄漏会导致打不开新连接）
    test_sock = socket.socket()
    test_sock.settimeout(5)
    try:
        test_sock.connect(('192.168.1.100', 502))
        test_sock.close()
        print("✅ 无连接泄漏")
    except socket.timeout:
        raise AssertionError("❌ 连接泄漏导致服务端卡死")
```

**为什么这是工业现场的真实需求**：
- 很多 PLC/控制器的 TCP 栈是嵌入式裁剪版，有连接数上限（如 8 个）
- 如果客户端崩溃后没 close，服务端泄漏 TIME_WAIT 连接，几次后就打不开了
- 供应商文档不会写"最多 8 个连接"，只能你试出来

### 1.6 面试话术模板

**问题**："如果只给你一个黑盒控制器通过 EtherCAT 通讯,怎么测?"

**答案**：
> "我会分三个层次测：
> 
> 1. **协议契约层** — 用 Wireshark 抓包,验证帧格式是否符合 EtherCAT 规范（工作计数器、CRC、命令类型）。用逻辑分析仪测周期抖动,P99 应在规格范围内。
> 
> 2. **异常注入层** — 物理拔插电缆模拟从站掉线,验证主站是否 2 秒内自动恢复。用 iperf3 打满总线带宽,看是否触发过载保护。故意发送非法帧（CRC 错误、非法命令）,验证是否有防御。
> 
> 3. **长时稳定性** — 连续跑 24 小时,监控丢包率、重传次数、内存占用。真实案例：某次发现 8 小时后开始丢包,定位是从站固件的内存泄漏,每个周期泄漏 1 字节,累积到阈值后崩溃。
> 
> **为什么这套方法不需要源码**：因为通讯协议是公开规范,我测的是'你是否遵守规范',而不是'你内部怎么实现'。即使看不到代码,物理手段（拔电缆、打流量）能触发所有边界。"

## 第 2 章 编译器 / 执行器

### 2.1 被测对象与典型形态

**被测对象**：
- **编译器**：把示教器录制的轨迹或高级语言（如 RAPID、KRL）编译成控制器可执行的字节码/中间表示
- **执行器（Interpreter/Runtime）**：控制器上的运行时环境，逐条解释执行指令，调度运动、IO、逻辑

**工业机器人常见形态**：
- **ABB RAPID → IRC5 控制器** — RAPID 是类 Pascal 语言，编译成私有字节码
- **KUKA KRL → KRC 控制器** — KRL 编译成 `.dat`/`.src` 二进制
- **FANUC TP → R-30iB 控制器** — TP（示教编程）编译成 `.ls` 程序文件
- **钱江自研语言 → 自研控制器** — 你可能遇到过公司内部的 DSL

**拿到的形态**：
- **L2 级**：有编译器 SDK（如某些品牌开放解析库）
- **L1 级**：只有编译器二进制 + 文档（如 `krl_compiler.exe`）
- **L0 级**：编译器在控制器固件里，只能通过示教器触发，看不到任何中间产物

### 2.2 测试策略矩阵

| 维度 | 编译器（Compiler） | 执行器（Runtime） |
|---|---|---|
| **契约测试** | 语法错误必报、语义正确必过、输出字节码可加载 | 指令集完整性、寄存器/栈正确性、错误码规范 |
| **异常注入** | 非法语法、越界引用、循环依赖、超长标识符 | 栈溢出、除零、死循环、非法跳转、资源耗尽 |
| **差分测试** | 同程序编译两次应字节码相同、跨版本兼容 | 同程序不同执行器结果应一致、仿真 vs 真机 |
| **专属测试** | 编译速度、错误消息可读性、优化级别影响 | 实时性（周期时间）、中断响应、任务调度 |

### 2.3 编译器核心测试点

#### A. 语法覆盖测试（Syntax Coverage）

**黑盒策略**：从文档提取所有语法规则，逐条覆盖。

**例子**：假设 KRL 文档说支持这些结构：
```krl
; 顺序
PTP {X 100, Y 200, Z 300}
; 分支
IF condition THEN ... ELSE ... ENDIF
; 循环
FOR i=1 TO 10
; 函数调用
CALL my_func(arg1, arg2)
```

**测试用例**：
```python
def test_krl_syntax_coverage():
    """编译器语法覆盖测试"""
    test_cases = [
        # 正向：每种语法的最简单形式
        ("PTP {X 0, Y 0, Z 0}", True, "基本PTP"),
        ("IF TRUE THEN PTP HOME ENDIF", True, "IF单分支"),
        ("FOR i=1 TO 5 ENDFOR", True, "空FOR循环"),
        
        # 负向：故意的语法错误
        ("PTP {X 0, Y 0", False, "缺少闭括号"),
        ("IF TRUE THEN", False, "缺少ENDIF"),
        ("FOR i=1", False, "FOR缺少TO"),
        
        # 边界：嵌套深度
        ("IF TRUE THEN IF TRUE THEN IF TRUE THEN PTP HOME ENDIF ENDIF ENDIF", True, "三层嵌套"),
        (generate_nested_if(100), None, "100层嵌套应报错或成功,不能挂死"),
    ]
    
    for code, expect_success, description in test_cases:
        result = compile_krl(code)  # 调用闭源编译器
        if expect_success is True:
            assert result.success, f"{description} 应编译通过但失败"
        elif expect_success is False:
            assert not result.success, f"{description} 应报错但通过了"
        # expect_success=None 表示"不能崩溃"，只检查返回
```

**关键**：
- 文档是规格，测试是审计 —— 文档说支持的必须测到
- 负向用例更重要 —— 很多编译器在非法输入时崩溃（segfault）而不是报错

#### B. 编译确定性（Deterministic Build）

**黑盒验证**：
```python
def test_deterministic_compilation():
    """同样源码多次编译，字节码应完全相同"""
    source = read_file("test_program.krl")
    
    bytecode1 = compile_krl_to_bytes(source)
    bytecode2 = compile_krl_to_bytes(source)
    
    # 应字节级相同（不含时间戳等元数据）
    assert bytecode1 == bytecode2, "编译不确定（可能嵌入了时间戳）"
```

**为什么这重要**：
- 不确定的编译器会导致版本控制噩梦（每次编译生成不同二进制，无法 diff）
- 工业现场要求"源码相同 = 行为相同"，时间戳污染会破坏这个假设

**真实案例**：
> "钱江的程序编译器每次会在字节码头部写入编译时间戳。导致同样的 `.src` 文件，不同时间编译出的 `.dat` 文件哈希值不同，版本管理工具无法判断'这两个程序是否相同'。我写了测试证明这个问题，建议把时间戳移到元数据区，编译核心保持确定性。"

> 
> 1. **参数边界** — 从手册提取所有参数范围（电流 50-500A、电压 10-50V），逐个测边界值和越界值。重点测**危险组合**（高电流+低电压），验证是否有互斥检查。真实案例：某焊机文档写支持 50A，实际控制器限制 100A，试出来后发现文档错了。
> 
> 2. **时序正确性** — 用高速 IO 采集卡记录起弧过程（送丝、送气、起弧）的时序，验证是否符合工艺要求（送气应在起弧前 20-50ms）。这需要硬件工具，但不需要源码。
> 
> 3. **异常恢复** — 焊接过程中触发急停，验证电弧是否立即熄灭（<10ms），以及能否恢复。某次测出急停后电弧延迟 100ms 才熄灭，烧穿了工件。
> 
> 4. **物理验证** — 用同样参数焊 10 条焊缝，切片检测熔深、气孔率。这是**工业机器人测试独有**的环节——软件测试不会做物理检测，但工业现场必须保证工艺质量。
> 
> **为什么不需要源码**：工艺效果是物理可测量的（力、电流、焊缝质量）。我测的是'参数设对了，结果是否符合工艺标准'，而不是'代码怎么写的'。"

## 第 4 章 算法接口（IK / 轨迹 / 运动学）

### 4.1 被测对象与典型形态

**被测对象**：
- **逆运动学（IK）**：给定末端目标位姿，求解关节角度
- **正运动学（FK）**：给定关节角度，计算末端位姿
- **轨迹规划**：给定起止点，生成平滑轨迹（考虑速度、加速度、关节限位）
- **奇异点检测**：识别运动学奇异配置（如肩肘腕共线）
- **碰撞检测**：判断给定姿态是否自碰撞或与环境碰撞

**拿到的形态**：
- **L2 级**：运动学库 `.so` + API 头文件（如 MoveIt、KDL、自研库）
- **L1 级**：只有编译好的 `.so`，无头文件，通过控制器接口间接调用
- **L0 级**：算法在控制器固件里，只能通过示教器触发，看不到任何中间结果

**特殊性**：这是**数学算法**，有明确的正确性定义（数学不变量）。即使看不到源码，也能用**数学性质**来验证。

### 4.2 测试策略矩阵

| 维度 | IK / FK | 轨迹规划 | 碰撞检测 |
|---|---|---|---|
| **契约测试** | FK∘IK=恒等、解在关节限位内、唯一解时确定性 | 速度/加速度连续、无超限、起止点精确到达 | 已知碰撞场景必检出、无碰撞场景不误报 |
| **异常注入** | 不可达位置、奇异点、四元数非归一化 | 起止点相同、零速度、极短/极长轨迹 | 边界接触（距离 0.001mm）、快速运动 |
| **差分测试** | 跨 IK 库对比（自研 vs MoveIt）、数值解 vs 解析解 | 不同规划器结果应可比、长轨迹分段拼接=整体 | 不同碰撞库（FCL vs Bullet）同场景应一致 |
| **性能基线** | 单次求解时间（<10ms）、收敛率（>95%） | 1000 点轨迹生成时间、规划成功率 | 复杂场景检测时间（<50ms） |

### 4.3 IK / FK 核心测试点

#### A. FK∘IK 往返一致性（最重要）

**数学不变量**：FK(IK(pose)) ≈ pose

```python
def test_fk_ik_roundtrip():
    """FK 和 IK 往返应回到原点"""
    ik_solver = IKSolver()  # 闭源库
    fk_solver = FKSolver()
    
    # 测试 100 个随机目标位姿
    for _ in range(100):
        # 生成工作空间内的随机位姿
        target_pose = generate_random_reachable_pose()
        
        # IK 求解
        joint_angles = ik_solver.solve(target_pose)
        if joint_angles is None:
            continue  # 不可达，跳过
        
        # FK 正向计算
        actual_pose = fk_solver.compute(joint_angles)
        
        # 位置误差应 <1mm
        pos_error = np.linalg.norm(actual_pose.position - target_pose.position)
        assert pos_error < 0.001, f"位置误差: {pos_error*1000:.2f}mm"
        
        # 姿态误差应 <0.1° (用四元数距离)
        ori_error = quaternion_distance(actual_pose.orientation, target_pose.orientation)
        assert ori_error < np.deg2rad(0.1), f"姿态误差: {np.rad2deg(ori_error):.3f}°"
```

**为什么这是黑盒的核心**：
- 不需要知道 IK 用什么算法（解析解、数值解、神经网络）
- 只需要验证数学性质：往返应回到原点
- **如果这个测试失败，IK 或 FK 至少有一个是错的**

    # 从配置文件读取关节限位（或从文档手动输入）

        (-170, 170),  # J1: ±170°
        (-120, 120),  # J2
        (-170, 170),  # J3
        (-185, 185),  # J4
        (-120, 120),  # J5
        (-360, 360),  # J6
    ]
    
    # 测试 1000 个随机位姿
    violations = []
    for i in range(1000):
        target_pose = generate_random_reachable_pose()
        joint_angles = ik_solver.solve(target_pose)
        
        if joint_angles is None:
            continue
        
        # 检查每个关节
        for j, (angle, (min_limit, max_limit)) in enumerate(zip(joint_angles, joint_limits)):
            angle_deg = np.rad2deg(angle)
            if not (min_limit <= angle_deg <= max_limit):
                violations.append({
                    'test_id': i,
                    'joint': j,
                    'angle': angle_deg,
                    'limit': (min_limit, max_limit)
                })
    
    if violations:
        print(f"❌ 发现 {len(violations)} 个关节限位违规:")
        for v in violations[:5]:  # 只打印前 5 个
            print(f"  测试 {v['test_id']}: J{v['joint']} = {v['angle']:.1f}° (限位 {v['limit']})")
        assert False, "IK 返回超限解"
    else:
        print("✅ 所有 IK 解在限位内")

```python
def test_ik_near_singularity():
    """测试奇异点附近 IK 的行为"""
    ik_solver = IKSolver()
    
    # 奇异配置 1：肩肘腕共线（J2=0, J3=0 for typical 6-axis）
    singular_joints = [0, 0, 0, 0, 0, 0]  # 伸直臂
    fk_solver = FKSolver()
    singular_pose = fk_solver.compute(singular_joints)
    
    # 在奇异点附近微扰（偏离 1mm）
    perturbed_pose = singular_pose.copy()
    perturbed_pose.position[1] += 0.001  # Y 方向 +1mm
    
    # IK 求解
    result = ik_solver.solve(perturbed_pose)
    
    # 契约 1：应有解（微扰应可达）
    assert result is not None, "奇异点附近微扰应有解"
    
    # 契约 2：解应稳定（不应跳变到完全不同的配置）
    joint_change = np.abs(result - singular_joints)
    max_change = np.max(joint_change)
    assert max_change < np.deg2rad(10), \
        f"奇异点附近解不稳定，最大跳变 {np.rad2deg(max_change):.1f}°"
```

**工业机器人的真实需求**：
- 奇异点附近速度会暴增（关节速度 → ∞）
- 很多 IK 算法在奇异点不收敛或返回错误解
- 必须验证"接近但不在奇异点"时的行为

def test_trajectory_continuity():
    """轨迹的速度和加速度应连续（无突变）"""
    planner = TrajectoryPlanner()
    
    # 规划简单直线轨迹
    start = [0, 0, 0, 0, 0, 0]
    goal = [np.pi/4, np.pi/4, 0, 0, 0, 0]

    velocities = np.diff(trajectory.positions, axis=0) / dt

    max_velocity_jump = np.max(velocity_jumps)
    assert max_velocity_jump < 0.01 * 1.0, \
        f"速度不连续，最大跳变 {max_velocity_jump:.3f} rad/s"
    
    # 检查加速度限制
    max_accel = np.max(np.abs(accelerations))
    assert max_accel <= 2.0 * 1.05, \  # 允许 5% 超限（数值误差）

### 4.7 面试话术模板

**问题**："如果只给你一个 IK 库的 `.so` 文件，没有源码也没有文档，怎么测？"

**答案**：
> "我会用**数学不变量**来测，因为运动学有明确的正确性定义：
> 
> 1. **FK∘IK 往返一致性** — 这是最核心的测试。随机生成 1000 个工作空间内的位姿，IK 求解后再用 FK 算回去，位置误差应 <1mm，姿态误差 <0.1°。如果往返回不来，FK 或 IK 至少有一个错了。
> 
> 2. **关节限位检查** — 从手册（或物理测量）得到关节限位，验证 IK 的所有解都在限位内。真实案例：某供应商的 IK 库返回 J1=185°，但机器人手册限位是 ±170°，实际运行会报错。
> 
> 3. **奇异点行为** — 构造已知奇异配置（如肩肘腕共线），在附近微扰 1mm，验证 IK 是否稳定。某次测出奇异点附近解跳变 >90°，机器人执行时会突然甩臂。
> 
> 4. **差分测试** — 如果有另一个开源 IK 库（如 MoveIt KDL），用同样输入对比结果。两者应在 1mm 内一致。不一致时，至少知道有问题，再手动验证谁对谁错。
> 
> **为什么不需要源码**：因为运动学是数学问题，正确答案可以用数学性质验证。FK∘IK=I 这个性质比任何文档都可靠。"

### 6.3 示教器硬件测试点

#### A. 按键响应可靠性

**黑盒策略**：物理按键测试，记录响应时间和失败率。

```python
def test_teach_pendant_button_response():
    """测试示教器按键响应"""
    pendant = TeachPendant()  # 通过串口或 USB 连接
    
    # 测试所有按键
    buttons = ['UP', 'DOWN', 'LEFT', 'RIGHT', 'ENTER', 'ESC', 
               'ENABLE', 'DEADMAN', 'ESTOP']
    
    results = {}
    for button in buttons:
        press_times = []
        fail_count = 0
        
        for trial in range(100):
            start = time.time()
            pendant.press_button(button)  # 手动按或自动化夹具
            
            response = pendant.wait_for_response(timeout=0.5)
            elapsed = time.time() - start
            
            if response:
                press_times.append(elapsed)
            else:
                fail_count += 1
        
        results[button] = {
            'mean_response': np.mean(press_times) if press_times else None,
            'max_response': np.max(press_times) if press_times else None,
            'fail_rate': fail_count / 100
        }
    
    # 契约：响应时间 <100ms，失败率 <1%
    for button, stats in results.items():
        if stats['mean_response']:
            assert stats['mean_response'] < 0.1
        assert stats['fail_rate'] < 0.01
```

## 第 8 章 面试话术与知识迁移映射

> 本章总结：如何把"闭源测试经验"转化为面试加分项，以及如何迁移到具身智能领域。

### 8.1 核心叙事框架（STAR 法则）

面试讲经历时，用 STAR 框架：

- **S (Situation)**：当时的背景，拿到的是什么形态（L0/L1/L2），为什么看不到源码
- **T (Task)**：面临什么问题，业务影响是什么
- **A (Action)**：你做了什么，用了什么方法 / 工具，遇到什么困难怎么克服
- **R (Result)**：最终效果，用数据说话（发现 X 个 bug、提升 Y% 成功率、缩短 Z 小时停机时间）

**例子**（钱江 EtherCAT 主站性能问题）：

> **S**: 钱江机器人的 EtherCAT 主站是供应商闭源库，只有 `.so` 文件和 API 文档，看不到内部实现。
> 
> **T**: 客户现场反馈机器人偶尔抖动，怀疑是通讯问题。我的任务是定位根因并提供解决方案。
> 
> **A**: 我用逻辑分析仪抓取 1 分钟总线波形，导出时间戳后用 Python 脚本统计周期间隔。发现 P99 延迟 1.2ms，超出 1kHz 周期要求。通过对比不同负载下的抖动分布，排除了网络硬件问题，定位是 **CPU 调度** —— 主站线程优先级不够，被其他任务抢占。我写了详细的测试报告，包括抖动分布图和对比实验，反馈给供应商。
> 
> **R**: 供应商在下个版本调整了线程优先级和 CPU 亲和性，P99 延迟降到 1.03ms，客户现场抖动问题消失。这个案例让我理解：**即使看不到源码，物理可测量的性能指标依然能定位问题**。

### 8.2 高频面试问题与标准答法

#### Q1: "你说你做过黑盒测试，具体是什么场景？"

**标准答法**：
> "在钱江做工业机器人测试时，经常遇到供应商提供的闭源库 —— 比如 EtherCAT 主站、运动控制算法、焊接工艺包。这些模块只有 `.so` 文件 + API 头文件，看不到实现。
> 
> 我的策略是：
> 1. **从接口入手** — 把 API 当规格书，大量边界值、异常输入、并发场景，验证是否遵守契约。
> 2. **物理手段** — 用示波器、万用表、逻辑分析仪测量实际输出，验证与文档是否一致。
> 3. **差分测试** — 如果有开源对比库（如 MoveIt 的 IK），用同样输入对比结果。
> 
> 举例：某次测试运动学库，我写了 **FK∘IK 往返一致性测试** —— 1000 个随机位姿，IK 求解后用 FK 算回去，位置误差应 <1mm。这个测试不需要知道 IK 用什么算法，只需要验证数学性质。结果发现 8% 的样本误差 >5mm，反馈后供应商修复了奇异点附近的数值不稳定问题。"

#### Q2: "工业机器人测试和具身智能测试有什么不同？"

**标准答法**：
> "核心思路是一样的 —— 都是验证 **感知 → 决策 → 执行** 的闭环是否可靠。但具体侧重点不同：
> 
> | 维度 | 工业机器人 | 具身智能 |
> |---|---|---|
> | **确定性** | 高度确定（同样输入 → 同样输出） | 概率性（神经网络输出有随机性） |
> | **测试焦点** | 运动学精度、实时性、安全合规 | 泛化能力、边界 case、数据质量 |
> | **仿真作用** | 辅助验证（真机为主） | 核心训练环境（Sim2Real） |
> | **故障模式** | 机械磨损、通讯丢包、参数越界 | 分布外数据、对抗样本、策略崩溃 |
> 
> **可迁移的技能**：
> - **运动学验证** — FK∘IK 往返测试、工作空间边界、奇异点检测，这些在具身智能里一样需要。
> - **硬件在环** — 工业机器人的"仿真 vs 真机对比"，对应具身智能的 **Sim2Real gap 测试**。
> - **异常注入** — 工业界测"传感器断线、电机过载"，具身智能测"遮挡、光照变化、物体滑脱"，思路相同。
> 
> 我在 DISCOVERSE 项目上做的测试，就是把工业机器人的**契约测试、差分测试、物理验证**思维迁移到具身智能仿真场景。"

#### Q3: "如果只给你一个编译好的控制器固件，没有任何文档，怎么测？"

**标准答法**：
> "这是最极端的黑盒场景（L0 级）。我会：
> 
> 1. **逆向协议** — 用 Wireshark 抓包，手动解析报文格式。对比不同操作下的报文差异，反推协议结构。某次我用这个方法还原了一个私有 Modbus 扩展协议的 70% 功能码。
> 
> 2. **试探边界** — 发送各种参数组合，观察响应。比如速度倍率从 0 试到 200，看哪个值被拒绝 → 反推合法范围。这种方法慢但可靠。
> 
> 3. **物理验证** — 控制器输出最终是物理动作（电机转、IO 变化）。用示波器测量实际输出，建立 **输入参数 → 物理行为** 的映射表。
> 
> 4. **对比法** — 如果有同类产品（如另一品牌机器人），用同样输入对比行为。行为一致的部分是"行业标准"，不一致的是"私有实现"。
> 
> 真实案例：某次拿到一个黑盒示教器，连接协议未知。我用逻辑分析仪抓串口数据，发现是 9600 波特率、8N1、Modbus RTU 变种。通过发送标准 Modbus 请求，定位功能码映射，最终写出了一套自动化测试脚本。"

### 8.3 工业机器人 → 具身智能的知识映射表

| 工业机器人经验 | 具身智能对应场景 | 迁移方式 |
|---|---|---|
| **运动学标定与精度验证** | 仿真环境的运动学准确性 | FK∘IK 测试、关节限位检查 |

### 8.4 简历上怎么写

**❌ 错误写法**（空洞）：
> 负责工业机器人测试，熟练使用 pytest 编写测试用例，发现并修复多个 bug。

**✅ 正确写法**（可量化、有细节）：
> 主导钱江机器人 EtherCAT 通讯模块黑盒测试，**在无源码情况下**，通过逻辑分析仪 + Python 脚本定位 P99 延迟超标问题（1.2ms → 1.03ms），消除客户现场抖动故障。
> 
> 设计并实现运动学算法契约测试框架，覆盖 FK∘IK 往返一致性、关节限位、奇异点稳定性，**发现供应商 IK 库 8% 样本误差 >5mm 的数值不稳定问题**，反馈后修复。
> 
> 搭建硬件在环测试平台（力传感器 + 标定夹具），验证焊接工艺包力控精度（±1N），提交 12 份缺陷报告，8 个安全关键问题被优先修复。

**关键**：
- 明确说"黑盒 / 无源码"，体现你的独特价值
- 用数字（X 个 bug、Y% 提升、Z ms 延迟）
- 说清方法（逻辑分析仪、FK∘IK 测试、力传感器）
- 说清影响（客户故障消除、安全问题修复）

### 8.5 最后的建议

1. **不要试图隐藏"看不到源码"这件事** — 这恰恰是你的差异化能力。纯软件测试候选人大多只会白盒测试，你会黑盒 + 硬件验证，这是稀缺技能。

2. **准备 2-3 个深度故事** — 每个故事能讲 5-10 分钟，包含完整的 STAR 过程 + 技术细节 + 可量化结果。面试时根据对方问题选一个展开。

3. **把"魔鬼日志"变成面试素材库** — 三周 DISCOVERSE 实践结束后，`docs/devil-log.md` 里的每一条"踩坑 → 排查 → 解决"记录，都可以转化成面试故事。

4. **主动展示思维方式，而非只讲结果** — 面试官想知道你"怎么想的"，不只是"做了什么"。比如讲 FK∘IK 测试时，强调"我选择数学不变量验证，是因为它不依赖源码可见性"。

5. **诚实面对不足** — 如果被问到没做过的（如神经网络对抗样本测试），诚实说"这块我还在学习，但我理解它和工业界异常注入测试的相似性是..."。真实比包装更有说服力。

- **接到新测试任务时** — 先判断被测对象属于哪个模块（通讯 / 编译器 / 工艺 / 算法 / HAL / HMI），翻到对应章节
- **遇到"没有源码"的困境时** — 回到第 0 章总论，重新审视可见性层级和三条主线
- **准备面试前** — 精读第 8 章，把自己的经历套进 STAR 框架

### 如何扩展

- 每次遇到新的黑盒测试场景，按本文的章节结构补充：被测对象 → 策略矩阵 → 核心测试点 → 工具 → 话术
- 三周 DISCOVERSE 实践中发现的测试方法，可以反向映射回本文档（如"仿真确定性测试"对应"编译器确定性"）

### 与主线计划的关系

- **本文档是旁支产出**，作为知识储备归档
- **主线仍是 DISCOVERSE 三周实战** — 开源 Python 白盒测试，建立完整链路思维
- 两者互补：白盒练"深度"，黑盒练"广度"，迁移后覆盖工业界绝大多数场景
